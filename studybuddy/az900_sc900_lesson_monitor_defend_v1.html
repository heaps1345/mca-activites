Section 01 — AZ-900

Azure Monitor

The single platform for collecting, analysing and acting on telemetry from your Azure resources and applications.

Azure Monitor is the umbrella service that sits across everything. When you hear "monitoring in Azure," this is it. It collects two core data types: MetricsNumeric time-series values collected at regular intervals. Think CPU %, memory usage, request count. Stored in a time-series database, lightweight and near real-time. and LogsStructured and unstructured event data — traces, exceptions, audit records. Stored in a Log Analytics workspace and queried with KQL (Kusto Query Language).. Metrics tell you how much. Logs tell you what happened.

📊

Azure Monitor Metrics

Platform metrics collected automatically from every Azure resource. CPU, memory, network throughput, HTTP queue length. Near real-time, up to 1-minute granularity. No agent needed for platform metrics.

📝

Log Analytics Workspace

The central data store for logs. Everything flows here — activity logs, diagnostic logs, App Insights data, Syslog. You query it with KQL. Sentinel also sits on top of this workspace.

🔍

Application Insights

APM (Application Performance Monitoring) for your code. Instrument your app to trace requests, dependencies, exceptions, and page views. Part of Azure Monitor. Supports adaptive sampling to control costs.

🔔

Azure Monitor Alerts

Fire notifications or trigger automated actions when metrics or log queries cross a threshold. Uses Action Groups to define who gets notified (email, SMS, webhook) and what runs (Logic Apps, autoscale, Azure Functions).

💡 Deep Dive: Metrics vs Logs — When to use which? ▼
Use Metrics when: you need real-time dashboards, autoscale triggers, or quick health checks. Metrics are fast (sub-minute latency), cheap (included free), and ideal for alerting on thresholds like "CPU > 80% for 5 minutes."

Use Logs when: you need to investigate root causes, correlate across services, or audit activity. Logs are richer but cost more (charged per GB ingested). A KQL query like requests | where duration > 2s | summarize count() by operation_Name can pinpoint exactly which API endpoint is slow.

The pattern: Metrics detect the problem → Alerts notify the team → Logs diagnose the cause.
🧠 Knowledge Check
Your web app is experiencing intermittent 500 errors. You need to find which dependency call is failing. Which Azure Monitor feature do you use?
Azure Monitor Metrics — check the HTTP 5xx metric
Application Insights — trace failed dependency calls
Azure Advisor — check reliability recommendations
Azure Service Health — check for platform outages
Metrics will show you that 500s are happening, but not why. Application Insights instruments your code to trace each request through its dependency chain — it'll show you exactly which external call (SQL, API, cache) failed and the exception it threw. Service Health only tells you about Azure platform issues, not your app's bugs. Advisor gives proactive recommendations, not real-time diagnostics.

Health Trio: Service Health, Resource Health & Advisor

Three services that sound similar but answer completely different questions. This is a favourite exam trap.

The exam loves presenting a scenario and asking which of these three you'd use. The trick is understanding whose problem you're investigating — Azure's infrastructure, your specific resource, or your overall best practices.

Azure Service Health answers: "Is Azure itself having problems?"

Three components:
→ Azure Status — global view of all Azure services across all regions (the public status page)
→ Service Health — personalised dashboard filtered to YOUR subscriptions, regions, and services
→ Health Advisories — planned maintenance, feature retirements, and upcoming changes that affect you

Use when: You suspect the problem isn't your code — it's Azure. "Is the UK South region having issues?" goes here.
Resource Health answers: "Is THIS specific resource affected by an Azure platform issue?"

→ Checks whether your VM, App Service, or SQL Database is impacted by an ongoing platform event
→ Shows current state: Available, Unavailable, Degraded, or Unknown
→ Links directly to relevant Service Health events if there's a platform issue

Use when: "My VM won't start — is it me or Azure?" Start at Resource Health to rule out platform issues before digging into your config.
Azure Advisor answers: "What should I be doing better?"

Five pillars of recommendations:
→ Reliability — availability zone usage, backup configuration
→ Security — integrates with Defender for Cloud recommendations
→ Performance — right-sizing, caching opportunities
→ Cost — underutilised resources, reserved instance opportunities
→ Operational Excellence — service health alerts, tagging

Use when: You're NOT fighting a fire. Advisor is proactive — it analyses your deployed resources and suggests improvements. No real-time monitoring.
⚠️ Exam Trap
"A VM is unresponsive — which service tells you if it's a platform issue?" → Resource Health, not Service Health. Service Health shows region/service-wide events. Resource Health checks YOUR specific resource. The exam tests this distinction repeatedly.
🧠 Knowledge Check

Resource Health — it shows upcoming impacts to your resources
Azure Advisor — under the Reliability pillar
Azure Service Health — in the Health Advisories section
Azure Monitor — via a planned maintenance metric alert
Health Advisories within Azure Service Health is where planned maintenance notices appear, filtered to your subscriptions and regions. Resource Health tells you the current state during/after the event, not in advance. Advisor recommends best practices, not maintenance schedules.
Section 03 — SC-900

Microsoft Defender for Cloud

Cloud security posture management and workload protection. Two pillars, one portal blade.

Defender for Cloud does two fundamentally different jobs under one roof. The exam absolutely loves testing whether you know the difference between them. Every Defender question maps back to this split:

CSPM — Cloud Security Posture Management
Secure Score — your security posture as a percentage
Security Recommendations — prioritised fixes
Regulatory Compliance dashboard
Cloud Security Graph & attack path analysis
Free tier (foundational CSPM) included for all Azure subscriptions
Think: "How secure IS my environment?"
CWP — Cloud Workload Protection
Defender for Servers — EDR, vulnerability assessment, JIT
Defender for App Service — web attack detection
Defender for SQL — injection detection, anomalous access
Defender for Key Vault — unusual secret access
Defender for Containers, Storage, DNS, ARM, etc.
Think: "Is someone attacking my workloads RIGHT NOW?"
🔒 Deep Dive: Secure Score — How it works ▼
Secure Score evaluates your resources against security controls. Each control groups related recommendations (e.g., "Enable MFA" is one recommendation within the "Manage access and permissions" control).

How scoring works:
→ Each control has a max score. Your score for that control = (compliant resources / total resources) × max score
→ Overall secure score = sum of all control scores / sum of all max scores × 100

The quick wins that move the needle most:
→ Enable MFA on privileged accounts (high weight, easy to do)
→ Enable JIT VM access (replaces always-open RDP/SSH)
→ Apply disk encryption
→ Remove public IPs from VMs that don't need them

Note: Resource tags and cost optimisation don't affect secure score — those are Advisor territory.
⚔️ Deep Dive: Defender for Servers — What Plan 2 gives you ▼
Plan 1 gives you Microsoft Defender for Endpoint (MDE) integration — EDR on your VMs. Basic threat detection.

Plan 2 adds everything from Plan 1 plus:
→ Qualys or Microsoft Defender Vulnerability Management (MDVM) for vulnerability assessment
→ Just-In-Time (JIT) VM access — time-limited, approval-based access to management ports
→ Adaptive Application Controls — ML-driven allowlisting of executables
→ File Integrity Monitoring (FIM)
→ Adaptive Network Hardening — tightens NSG rules based on actual traffic

For the SC-900 exam, know the features exist and which plan they belong to. You won't need deep config, but you need to map capability → product.
🧠 Knowledge Check
A SQL injection attempt is detected on your Azure SQL database. Which Defender for Cloud pillar generated this alert?
CSPM — it was flagged as a security recommendation
CWP — Defender for SQL detected a runtime attack
CSPM — it reduced the secure score
Azure Advisor — under the security pillar
SQL injection detection is a runtime threat — that's CWP (Cloud Workload Protection), specifically Defender for SQL. CSPM would tell you "you should enable auditing on your SQL server" as a recommendation, but it doesn't detect active attacks. That's the core distinction: CSPM = posture, CWP = protection.
🧠 Knowledge Check
Which Defender for Cloud capability is available for FREE on every Azure subscription?
Foundational CSPM — secure score and recommendations
Defender for Servers Plan 1
Advanced cloud security graph and attack path analysis
All CWP plans for the first 30 days
Foundational CSPM is free — you get secure score, basic recommendations, and the regulatory compliance dashboard. The enhanced CWP plans (Servers, SQL, App Service, etc.) cost per resource per month. Defender for Cloud CSPM (advanced) with attack path analysis is also a paid upgrade. There IS a 30-day trial, but that's not the "free" tier — it's a trial.

Microsoft Sentinel

Cloud-native SIEM + SOAR. Aggregates signals from everywhere and automates response.

Sentinel is where everything comes together. It doesn't generate its own alerts — it ingests them from Defender for Cloud, Entra ID Protection, M365 Defender, third-party firewalls, and anything else you connect. Then it correlates, detects patterns, and automates response.

📡 The Four Pillars of Sentinel ▼
1. Collect — Data connectors pull in logs from 100+ sources: Entra ID, M365 Defender, Defender for Cloud, AWS, firewalls (Syslog/CEF), threat intelligence feeds (STIX/TAXII).

2. Detect — Analytics rules run KQL queries on schedule to find threats. Built-in templates, custom rules, or ML-based anomaly detection. When a rule matches, it creates an incident.

3. Investigate — Investigation graph visualises entities (users, IPs, hosts) and their relationships. Hunting queries let you proactively search for threats the rules haven't caught. Workbooks provide dashboards.

4. Respond — Playbooks (built on Azure Logic Apps) automate response. Examples: isolate a compromised VM, disable a risky user, open a ServiceNow ticket, send a Teams alert. This is the SOAR capability.
⚠️ Critical Exam Distinction
Sentinel = SIEM + SOAR (Security Information & Event Management + Security Orchestration, Automation & Response)
M365 Defender = XDR (Extended Detection & Response)

They integrate tightly, but the exam asks you to classify them. "Which Microsoft product is a SIEM?" → Sentinel. "Which is XDR?" → M365 Defender. Sentinel sits on a Log Analytics workspace — that's where all the data lives.

🧠 Knowledge Check
An automation rule in Sentinel triggers when a high-severity incident is created, automatically isolating the affected VM and notifying the SOC lead. What Sentinel feature performs this automated response?
Analytics Rule — it detected and responded to the threat

Playbooks are Logic Apps that execute automated response actions — this is the SOAR capability. Analytics rules detect and create incidents. Hunting queries are manual, analyst-driven. Workbooks are dashboards only — no automation. The chain is: Analytics Rule detects → creates Incident → Automation Rule evaluates → triggers Playbook.
Section 05 — SC-900

Microsoft Entra ID Protection

Automated identity risk detection and remediation. The identity security layer.

Entra ID Protection uses Microsoft's threat intelligence and ML models to detect identity-based risks in real time. It feeds into Conditional Access for automated remediation — and its alerts flow into Sentinel for SOC visibility. It operates on two risk types:

Sign-in Risk
Impossible travel — London to Moscow in 4 minutes
Anonymous IP address — Tor exit node sign-in
Malware-linked IP address
Unfamiliar sign-in properties
Password spray detected
Is this specific sign-in attempt suspicious?
User Risk
Leaked credentials — found on dark web paste
Azure AD Threat Intelligence — Microsoft flags the account
Anomalous user activity patterns
User confirmed compromised by admin
Accumulation of sign-in risk signals over time
Is this user account itself compromised?
🔗 How ID Protection connects to Conditional Access ▼
The real power is in the integration with Conditional Access policies:

Sign-in risk policy: "If sign-in risk is High → require MFA." This means the impossible-travel sign-in gets challenged with MFA before it's allowed. If the real user confirms with MFA, the risk is auto-remediated.

User risk policy: "If user risk is High → require password change." If credentials are found on the dark web, the user is forced to change their password at next sign-in (with MFA verification first).

This is automated remediation — no SOC analyst needs to intervene for common identity threats. The alerts still flow to Sentinel for visibility and correlation with other signals.
🧠 Knowledge Check
A user's credentials are found on a dark web paste site. Entra ID Protection flags this. What type of risk is this?
Sign-in risk — because the next sign-in will be suspicious
User risk — the account itself is compromised regardless of sign-in
Application risk — the app credentials are exposed
Device risk — handled by Microsoft Intune
Leaked credentials = user risk. The account is compromised whether or not anyone has signed in with those credentials yet. Sign-in risk evaluates individual sign-in events (where, when, how). The leaked creds policy should force a password reset on next sign-in. The distinction matters because the remediation actions differ — sign-in risk → require MFA. User risk → require password change.
🧠 Knowledge Check
Where do Entra ID Protection risk detections appear in a SOC's unified view?
Azure Monitor — as identity metrics
Defender for Cloud — in the secure score
Azure Advisor — under security recommendations
Microsoft Sentinel — via the Entra ID data connector
ID Protection alerts flow into Sentinel through the Microsoft Entra ID data connector (sign-in logs and audit logs). This is how the SOC gets a unified view — identity risks from Entra, workload alerts from Defender, and everything else, all correlated in Sentinel. Defender for Cloud's secure score doesn't include identity risk detections — that's posture, not detection.

Your apps and VMs generate telemetry — requests, exceptions, performance metrics, OS-level events. This flows to Azure Monitor (platform metrics + logs) and Defender for Cloud (workload protection alerts).
Every sign-in, MFA challenge, conditional access decision, and directory change generates Entra ID logs. Entra ID Protection evaluates risk in real time. High-risk events trigger Conditional Access policies.
Azure's own infrastructure generates health events — outages, degradation, planned maintenance. Service Health tracks region/service status. Resource Health checks your specific resource.
Azure Monitor collects metrics and logs from everything. App Insights adds application-level tracing. Alerts fire when thresholds are crossed. All log data lands in a Log Analytics workspace.
Entra ID Protection detects risky sign-ins and risky users using ML models trained on billions of sign-in events. It feeds risk signals to Conditional Access for automated remediation (require MFA, force password reset, block).
Service Health = "Is Azure having problems?" Resource Health = "Is MY resource affected?" Advisor = "What should I improve?" None of these detect attacks — they're operational health and best practice tools.

Leaked credentials and anonymous IP sign-in are Entra ID Protection alerts (user risk + sign-in risk).
