DNS Enumeration and Zone Transfer Attempts

Query DNS record types using dig, enumerate subdomains, and attempt a zone transfer to map the target's DNS infrastructure. DNS enumeration is considered semi-passive - queries go to public DNS servers, not the target directly.

🔎 Pre-Flight Checks

No VMs required. Queries go to public DNS infrastructure only.

  • Kali Linux terminal is open
  • Internet access confirmed (ping 8.8.8.8)
🚀

Away you go!

All pre-flight checks complete. You are ready to start the lab.

Scenario

You are in the passive reconnaissance phase of an engagement against Syntex Solutions Ltd. You have identified their primary domain. Now map their DNS infrastructure - name servers, mail exchangers, subdomains, and any misconfigured zone transfers - before beginning any active scanning.

Learning Objectives
  • Query each DNS record type using dig
  • Identify name servers, mail servers, and SPF/DMARC policy records
  • Attempt a zone transfer (AXFR) and understand why it usually fails
  • Enumerate subdomains using forward brute force
  • Perform reverse DNS lookups against discovered IP addresses

Part 1 - Basic dig Queries
1
Query individual record types

Use dig to query specific DNS record types. We use bbc.co.uk as a publicly accessible example.

# A record - primary IPv4 address
dig bbc.co.uk A

# Name servers
dig bbc.co.uk NS

# Mail exchangers
dig bbc.co.uk MX

# TXT records (SPF, DMARC, verification tokens)
dig bbc.co.uk TXT

# SOA - get admin email from the second field
dig bbc.co.uk SOA
Record your findings
2
Query a specific DNS server

The @server syntax directs the query to a specific resolver. This is useful for comparing responses from different resolvers or querying the authoritative server directly.

# Query Google's public DNS
dig @8.8.8.8 bbc.co.uk A

# Query the authoritative NS directly (replace with NS from Step 1)
dig @ns1.bbc.co.uk bbc.co.uk A
ℹ
Querying the authoritative server directly bypasses caching and returns the live DNS state. This is useful when you suspect a zone is being served differently to different resolvers.
Part 2 - Zone Transfer Attempt
🎯
CREST Exam Focus: A successful AXFR gives you every DNS record in the zone - a complete map of internal and external hosts. Examiners expect you to know the command and what it reveals.
3
Attempt a zone transfer (AXFR)

A DNS zone transfer (AXFR query) requests a full copy of all DNS records in a zone from the authoritative name server. Misconfigured servers allow this from any source - a serious information disclosure vulnerability.

# Attempt AXFR - replace NS with an NS you found in Step 1
dig @ns1.bbc.co.uk bbc.co.uk AXFR

# Most modern servers refuse this - you will see "Transfer failed" or REFUSED
# zonetransfer.me is a deliberately vulnerable domain for practice
dig @nsztm1.digi.ninja zonetransfer.me AXFR
✓
zonetransfer.me is intentionally configured to allow zone transfers for security training. Run the AXFR against it and examine the output - this is what a successful zone transfer looks like.

Part 3 - Subdomain Enumeration
4
Forward brute-force subdomain enumeration

When zone transfers fail, enumerate subdomains by brute-forcing common names. dnsrecon and dnsenum automate this.

# dnsrecon - standard enumeration with default wordlist
dnsrecon -d bbc.co.uk -t std

# Brute force subdomains using a wordlist
dnsrecon -d bbc.co.uk -t brt -D /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt

# dnsenum - combines WHOIS, zone transfer attempt, and brute force
dnsenum --noreverse bbc.co.uk
How many subdomains were discovered?
5
Reverse DNS lookup

A PTR lookup resolves an IP address back to a hostname. This reveals server names for IPs you have discovered and can identify internal naming conventions.

# Single reverse lookup
dig -x 212.58.244.22

# Or use host command
host 212.58.244.22

# Reverse lookup a whole subnet (slow but thorough)
for i in $(seq 1 254); do host 212.58.244.$i 2>/dev/null | grep "domain name"; done
What hostname resolves for 212.58.244.22?

Q3

A zone transfer attempt against a target's name server returns "Transfer failed." What does this tell you, and what alternative enumeration technique would you use?

Transfer failed means the name server is configured to refuse AXFR requests from unauthorised sources - this is correct security practice. As an alternative, use brute-force subdomain enumeration with a wordlist (dnsrecon -t brt or dnsenum). You can also use certificate transparency logs (crt.sh) to find subdomains that have had TLS certificates issued - this is entirely passive and often more complete than wordlist brute force.
Q4

You find the SOA record for a target domain. The SOA contains the field: hostmaster.target.com. What does this reveal?

The SOA record's second field is the administrator's email address with the first dot replaced by @. So hostmaster.target.com translates to hostmaster@target.com. This is an email address you can use for phishing, password reset attacks, or LinkedIn OSINT to identify the DNS administrator. Combined with the MX record, you know where to send the phishing email.

★
Lab Complete - Key Takeaways: DNS enumeration is one of the highest-yield passive recon techniques. A single domain can reveal dozens of hosts through MX, NS, and subdomain records. Zone transfers are rare windfalls - most organisations block them - but still worth attempting on every engagement. TXT records reveal the full email infrastructure via SPF. Reverse DNS maps IPs to hostnames and can reveal internal naming conventions.
