Web Reconnaissance and Technology Fingerprinting

Extract intelligence from a target's web presence without triggering IDS alerts - HTTP headers, robots.txt, archived content, job adverts, and WhatWeb fingerprinting all reveal infrastructure details before a single port scan runs.

🔎 Pre-Flight Checks

No VMs required. All reconnaissance is against public web infrastructure.

  • Kali Linux terminal is open
  • Firefox or Chromium is available for web browsing

Scenario

You have identified Syntex Solutions Ltd's primary website. Before any active scanning, extract as much intelligence as possible from their web presence using passive and semi-passive techniques. The goal is to identify technologies, server software, and content paths that inform your later testing.

Learning Objectives
  • Retrieve and interpret HTTP response headers for technology disclosure
  • Analyse robots.txt and sitemap.xml for hidden paths
  • Use the Wayback Machine to recover deleted content
  • Extract intelligence from job advertisements
  • Use WhatWeb to fingerprint server technologies
Part 1 - HTTP Headers
1
Retrieve HTTP response headers

HTTP response headers often disclose the web server version, framework, and security configuration. This is the first thing to check on any web target.

# Fetch headers only with curl (HEAD request)
curl -I https://syntexsolutions.net

# Follow redirects and show final headers
curl -sI -L https://syntexsolutions.net

# Verbose output shows request AND response headers
curl -v https://syntexsolutions.net 2>&1 | grep -E "^[<>]"
ℹ
Key headers to look for: Server (web server and version), X-Powered-By (framework - PHP, ASP.NET), X-AspNet-Version, Via (CDN or proxy), Set-Cookie (session cookie names reveal frameworks - PHPSESSID = PHP, ASP.NET_SessionId = ASP.NET).

Part 2 - robots.txt and sitemap.xml
2
Check robots.txt for hidden paths

The robots.txt file instructs search engine crawlers which paths to ignore. Those disallowed paths are often the most interesting ones for testers.

# Fetch robots.txt
curl https://syntexsolutions.net/robots.txt

# Check sitemap.xml for all indexed content
curl https://syntexsolutions.net/sitemap.xml | head -50
⚠
robots.txt is NOT a security control. It is a crawling suggestion to search engines - nothing more. Attackers ignore it completely. A Disallow: /admin entry does not prevent access to /admin; it advertises that the path exists. Every Disallow entry is a recon lead, not a barrier.
🎯
CREST Exam Focus: The exam specifically tests whether you know robots.txt is NOT a security control. Disallow entries disclose paths the owner does not want indexed - these are often admin panels, staging areas, or legacy directories. The correct answer is always: robots.txt provides no access restriction whatsoever.
What did robots.txt reveal?
3
Query the Wayback Machine for archived content

The Wayback Machine at web.archive.org archives public websites over time. Deleted pages, old configuration files, and former directory listings may still be accessible.

# Check what years/dates have been archived
# Browse to: https://web.archive.org/web/*/syntexsolutions.net

# Use the CDX API to list all archived URLs for a domain
curl "https://web.archive.org/cdx/search/cdx?url=syntexsolutions.net&output=text&fl=original&collapse=urlkey&limit=50"
✓
Look for: old login pages, admin interfaces, API endpoints, backup files (.bak, .old), and configuration files (.conf, .cfg) in archived URLs. These may still be live even if removed from current site navigation.

Part 3 - Technology Fingerprinting
4
WhatWeb - automated technology detection

WhatWeb fingerprints web technologies from HTTP headers, HTML source, cookies, and JavaScript. It identifies CMS, frameworks, hosting, and CDNs in a single scan.

# Basic scan
whatweb https://syntexsolutions.net

# Verbose output with all plugin matches
whatweb -v https://syntexsolutions.net

# Aggressive mode - follow more links (semi-active, use carefully)
whatweb -a 3 https://syntexsolutions.net
What technologies did WhatWeb identify?
5
View page source for additional intelligence

HTML source often contains comments, version strings, internal paths, and references to JavaScript files that reveal the technology stack and sometimes internal infrastructure.

# Download and search source for comments and version strings
curl -s https://syntexsolutions.net | grep -iE "version|generator|powered|comment|internal|/api/"

# Look for HTML generator meta tag
curl -s https://syntexsolutions.net | grep -i "generator"
⚠
HTML comments like <!-- TODO: remove debug endpoint --> or <!-- internal: api.internal.corp.com --> are surprisingly common and reveal internal infrastructure names.
Part 4 - Exam-Style Questions
🎯
Answer without looking at notes.
Q1

A target's HTTP response includes the header X-Powered-By: ASP.NET and a cookie named ASP.NET_SessionId. What does this tell you about the technology stack?

The server is running Microsoft ASP.NET on IIS (Internet Information Services). The X-Powered-By header directly discloses the framework. The ASP.NET_SessionId cookie name confirms ASP.NET even if the header was removed. This tells you the target is Windows-based, running .NET Framework or .NET Core, and you should focus your vulnerability research on known ASP.NET CVEs and IIS misconfigurations.
Q2

Why are entries in a target's robots.txt Disallow list valuable to a tester?

robots.txt Disallow entries tell search engines not to index those paths - which means the owner is intentionally hiding them. Disallowed paths are often admin panels (/admin/, /wp-admin/), staging directories (/staging/, /dev/), API endpoints (/api/internal/), or legacy applications (/legacy/, /old/). A tester should manually check every disallowed path as these are frequently underprotected.

Q4

During web recon you find a job advert for a "Senior PHP/Laravel Developer" for the target company. What does this tell you about their infrastructure that would not be available from HTTP headers?

The job advert confirms the target runs PHP and specifically the Laravel framework - even if they have removed X-Powered-By headers. This lets you focus testing on Laravel-specific vulnerabilities (mass assignment, debug mode exposure, .env file disclosure at /.env) and PHP-specific issues. Job ads are a high-value passive recon source because organisations cannot suppress them without stopping recruitment.
