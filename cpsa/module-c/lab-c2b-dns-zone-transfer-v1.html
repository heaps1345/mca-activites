Background - What is a Zone Transfer?

A DNS zone contains every record for a domain - A records mapping hostnames to IPs, MX records for mail, CNAMEs for aliases, TXT records for services and policies. Zone transfers (AXFR queries) exist so secondary name servers can replicate zone data from the primary.

⚠
The vulnerability: When a name server is configured to allow AXFR from any source (not just trusted secondaries), any attacker can request a complete copy of the zone. This exposes internal hostnames, IP addresses, service names, and infrastructure detail that should never be publicly visible.
🎯
CREST Exam Focus: Know the dig AXFR syntax, what the output looks like, and why unrestricted AXFR is a vulnerability. Examiners may ask you to identify it in a scan output or explain the remediation.
TermWhat it means
AXFRFull zone transfer - returns all records in the zone
IXFRIncremental zone transfer - returns only changes since a serial number
SOAStart of Authority - the first record returned; contains the zone serial and admin email
allow-transfer { any; };BIND9 misconfiguration that allows any host to request a zone transfer
Secure configurationallow-transfer { 10.0.0.2; }; - restrict to trusted secondary NS IPs only
Part 1 - Locate the Name Server
1
Query NS records to find the authoritative name server

Before attempting a zone transfer, identify the authoritative name server for the domain. NS records tell you where to direct your AXFR request.

# Query the authoritative NS records for the target domain
dig syntexsolutions.net NS

# Also check the SOA for the primary NS and admin email
dig syntexsolutions.net SOA
ℹ
The SOA record's second field is the zone administrator's email address - the first dot is replaced by @. So admin.syntexsolutions.net in the SOA means admin@syntexsolutions.net. Record this - it is a recon finding.
Record your findings
Part 2 - Perform the Zone Transfer
2
Request a full zone transfer with dig AXFR

The AXFR query type requests a full copy of the zone. Direct it at the authoritative name server using the @server syntax.

# Zone transfer via the authoritative NS (once DNS propagates)
dig axfr syntexsolutions.net @ns1.syntexsolutions.net

# If DNS hasn't propagated yet, query the server directly by IP
dig axfr syntexsolutions.net @20.24.202.6

# Pipe to less for easier reading
dig axfr syntexsolutions.net @20.24.202.6 | less

# Count the total records returned
dig axfr syntexsolutions.net @20.24.202.6 | grep -v "^;" | grep -v "^$" | wc -l
✓
A successful AXFR begins with the SOA record and ends with the SOA record again. If you see ;; Transfer failed. or REFUSED, the server is correctly configured and rejecting your request. Against syntexsolutions.net, you should receive the full zone.
Zone transfer result
3
Save the zone output to a file

Capture the full zone to a file for analysis. On a real engagement this goes into your evidence folder.

# Save the full zone transfer output
dig axfr syntexsolutions.net @20.24.202.6 > syntex_zone.txt

# Verify it captured properly
wc -l syntex_zone.txt
head -20 syntex_zone.txt

# Strip comments and blank lines - clean record list only
grep -v "^;" syntex_zone.txt | grep -v "^$" | grep -v "^$" > syntex_clean.txt
Part 3 - Analyse the Zone Output
4
Extract A records - hosts and IP addresses

A records map hostnames to IP addresses. In a zone transfer these reveal every named host in the organisation's DNS - including internal ones that should never be public.

# Filter all A records from the zone
grep "\bIN\b.*\bA\b" syntex_zone.txt | grep -v AAAA

# Sort and deduplicate IPs
grep "\bIN\b.*\bA\b" syntex_zone.txt | awk '{print $NF}' | sort -u

# Look for internal-looking names (dev, internal, staging, vpn, mgmt...)
grep "\bIN\b.*\bA\b" syntex_zone.txt | grep -iE "dev|internal|staging|vpn|mgmt|admin|test|priv|db|sql|backup"
ℹ
Look for hostnames that hint at internal infrastructure: dev-, internal-, staging-, mgmt-, db-, vpn-. These are hosts the organisation assumed were private - they are now in your target list.
A records - what did you find?
5
Extract TXT records - breadcrumbs and intelligence

TXT records often contain far more than SPF and DMARC. Administrators use them for domain verification tokens, internal notes, and service markers - many of which were never intended to be public.

# Extract all TXT records
grep "\bTXT\b" syntex_zone.txt

# Look specifically for non-standard content
grep "\bTXT\b" syntex_zone.txt | grep -v "v=spf" | grep -v "v=DMARC"
⚠
The syntexsolutions.net zone contains TXT records with breadcrumbs - notes, internal references, and hints that a penetration tester would document and explore further. Read them carefully.
TXT record findings
6
Extract MX, CNAME, and SRV records

MX records reveal the mail infrastructure. CNAME records expose hosting providers and internal aliases. SRV records may reveal internal services (VoIP, XMPP, etc).

# Mail exchangers
grep "\bMX\b" syntex_zone.txt

# CNAME aliases (may reveal hosting providers or CDNs)
grep "\bCNAME\b" syntex_zone.txt

# SRV records (internal services)
grep "\bSRV\b" syntex_zone.txt

# NS records (additional name servers)
grep "\bNS\b" syntex_zone.txt
Service infrastructure
Part 4 - Document the Finding

⚠ Vulnerability: Unrestricted DNS Zone Transfer (AXFR)

The name server at 20.24.202.6 (ns1.syntexsolutions.net) is configured with allow-transfer { any; }; in BIND9, permitting any host to retrieve a complete copy of the DNS zone.

CVSSv3 Base Score: 5.3 (Medium) - Network, Low complexity, No privileges required, No user interaction, Low confidentiality impact

Impact: Full DNS zone enumeration including internal hostnames, IP addresses, and service records not intended for public disclosure.

Remediation: Replace allow-transfer { any; }; in /etc/named.conf with allow-transfer { <secondary-NS-IP>; }; - restricting transfers to trusted secondary name servers only.

Part 5 - Exam-Style Questions
🎯
Answer without looking at notes. These test understanding, not memorisation.
Q1

Write the dig command to perform a full zone transfer of target.com against name server ns1.target.com.

Q2

A zone transfer returns the output below. What does the first and last record type tell you about the transfer?

syntexsolutions.net.  3600  IN  SOA  ns1.syntexsolutions.net. ...
...
syntexsolutions.net.  3600  IN  SOA  ns1.syntexsolutions.net. ...
A successful AXFR response is always bounded by the SOA record - the zone starts and ends with it. The first SOA marks the beginning of the zone transfer, and the second SOA marks the end. If you only see one SOA and an error, the transfer was incomplete. The SOA record also contains the zone serial number, which tells you how recently the zone was updated, and the administrator's email address.
Q3

The zone transfer reveals a record: internal-erp.syntexsolutions.net. IN A 10.0.5.20. Why is this significant even though 10.0.5.20 is a private (RFC 1918) address?

Even though 10.0.5.20 is not directly reachable from the internet, the hostname reveals the existence of an internal ERP system. An attacker who later gains any internal access (via phishing, VPN compromise, or a foothold on a DMZ host) now has a pre-built target list including the server name and its internal IP. The naming convention also tells you the system is an ERP - which suggests a high-value target for business data. Recon intelligence compounds over time: a private IP today becomes a pivot target tomorrow.

Q5

During a zone transfer you find the record: _autodiscover._tcp.syntexsolutions.net. IN SRV 0 0 443 mail.syntexsolutions.net.. What does this tell you?

This is a Microsoft Exchange Autodiscover SRV record. It tells you the organisation is running a Microsoft mail platform (Exchange or Exchange Online / Microsoft 365) and that the autodiscover service is reachable at mail.syntexsolutions.net on port 443 (HTTPS). This is a valuable recon finding - it confirms the email platform, reveals a hostname to investigate, and the autodiscover endpoint is a known target for credential harvesting and internal relay abuse. On an engagement, you would attempt to access https://mail.syntexsolutions.net/autodiscover/ and check for legacy Exchange endpoints like OWA, EWS, and ActiveSync.
★
Lab Complete - Key Takeaways: A successful zone transfer is one of the highest-yield findings in passive reconnaissance - it hands you the organisation's entire DNS map in a single query. The AXFR syntax is dig axfr <domain> @<nameserver>. Always attempt it against every NS record you find. The vulnerability is the BIND9 misconfiguration allow-transfer { any; }; - remediation is restricting transfers to trusted secondary NS IPs only. TXT records in a zone often contain intelligence beyond SPF - read every one.
