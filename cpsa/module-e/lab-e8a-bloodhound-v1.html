Lab E8-A: BloodHound and Attack Path Analysis

Module E Active Directory CREST CPSA Syntex Solutions Ltd Difficulty: Intermediate Estimated time: 60 min

Why BloodHound Changes Everything

Active Directory is not a flat list of users and computers. It is a web of relationships - group memberships, delegation settings, ACL permissions, active logon sessions - and those relationships chain together into attack paths that no manual enumeration can reliably find.

BloodHound uses graph theory to model the entire domain as a network of nodes (users, computers, groups) and edges (the relationships between them). It then runs mathematical shortest-path algorithms across that graph to answer one question: what is the shortest chain of relationships that takes a low-privilege user to Domain Admin?

This is not a convenience tool. In complex environments BloodHound finds paths that would take days of manual analysis to discover - paths that defenders have never seen because they only look at individual permissions, never the chain.

Engagement Scenario

You have obtained low-privilege domain credentials for jsmith on the Syntex Solutions domain (syntex.local). Your objective is to use BloodHound CE to map the full attack surface, identify the shortest path to Domain Admin, and document the chain of relationships that makes it possible. No exploitation yet - this is the reconnaissance phase that makes every subsequent attack purposeful.

Learning Objectives

  • Understand why graph-based analysis exposes attack paths that manual enumeration misses
  • Start BloodHound CE and ingest domain data using bloodhound-python
  • Run the key built-in queries and interpret what each result means operationally
  • Identify and document a complete attack path from jsmith to Domain Admin
  • Understand what each BloodHound edge type means and why it is exploitable

Starting BloodHound CE

Setup
Why this matters

BloodHound CE replaced the legacy BloodHound/neo4j stack. It runs as a self-contained web application - no separate database setup required. The web UI is significantly better than the old Electron app and is now the standard tool for AD attack path analysis in professional assessments.

BloodHound CE is included in Kali 2025.2+. Start it with:

# Start BloodHound CE (runs Neo4j + API server + web UI)
sudo bloodhound-ce start

# First run takes ~60 seconds to initialise the database
# Watch for: "BloodHound CE is ready"

# If not installed:
sudo apt install bloodhound-ce -y

Open the web UI in your browser:

https://localhost:8080

# Default credentials on first run:
Username: admin
Password: (shown in terminal output on first start - copy it)

# You will be prompted to change the password on first login
ℹ
Browser Certificate Warning: BloodHound CE uses a self-signed certificate. Accept the warning in your browser - this is expected in a lab environment. In a real engagement you would run BloodHound CE behind a proper certificate.

Collecting Domain Data with bloodhound-python

Data Collection
Why we collect from Kali, not the target

SharpHound.exe runs on Windows and is the traditional collector - but it gets flagged by AV and leaves artefacts on the target. bloodhound-python runs entirely from Kali over LDAP and SMB using valid credentials. No binary touches the target. Same data, zero footprint on the Windows machine. This is the preferred method on professional engagements.

Run bloodhound-python against the Syntex domain. The -c All flag collects everything - users, groups, computers, sessions, ACLs, trusts, and GPOs:

# Collect all AD data from Kali
bloodhound-python \
  -u jsmith \
  -p Password1 \
  -d syntex.local \
  -ns <DC01-IP> \
  -c All \
  --zip

# --zip packages everything into a single .zip for easy import

Expected output:

INFO: Found AD domain: syntex.local
INFO: Getting TGT for user
INFO: Connecting to LDAP server: SYNTEX-DC01.syntex.local
INFO: Found 1 domains
INFO: Found 1 domain controllers
INFO: Found 12 computers
INFO: Found 47 users
INFO: Found 8 groups
INFO: Found 3 GPOs
INFO: Found 24 OUs
INFO: Enumeration done, writing json files
INFO: Compressing output into 20241021_bloodhound.zip
★
CREST CPSA Exam Point: Know both collectors. SharpHound collects session data more reliably (it queries each machine directly). bloodhound-python is stealthier and runs from Linux. For CPSA you need to know what each collects and why sessions are the most operationally valuable data type - because they show where privileged credentials are in memory right now.

Understanding BloodHound Edge Types

Concepts
Why edges are the attack

In BloodHound, nodes are objects (users, computers, groups). Edges are relationships between them. Every edge represents something an attacker can do - not just a piece of information, but an action that moves them closer to Domain Admin. Understanding what each edge means is the difference between reading a BloodHound graph and actually using it.

MemberOf

User or group is a member of another group. Chains of MemberOf can grant inherited privileges the account owner is unaware of.

HasSession

A user has an active logon session on a computer. Their credentials are in LSASS memory on that machine right now. Lateral movement to that host = credential capture.

AdminTo

A user or group has local admin rights on a computer. Allows remote code execution via PsExec, WMI, or WinRM without any exploitation.

GenericWrite

Permission to write arbitrary attributes on an object. On a user: set their SPN for Kerberoasting. On a group: add yourself as a member.

WriteDACL

Permission to modify the object's ACL. Grants the ability to give yourself any permission - effectively full control without appearing in AdminTo.

DCSync

The account has replication rights on the domain. DCSync dumps all password hashes from Active Directory without touching LSASS. Instant full domain compromise.

ForceChangePassword

Permission to reset another account's password without knowing the current one. Change a DA's password and log in as them.

Kerberoastable

Account has a registered SPN. Any authenticated user can request a TGS ticket encrypted with this account's hash and crack it offline.

5

Running the Key Queries

Analysis
Why query order matters

BloodHound has dozens of built-in queries. On a real engagement you don't run all of them - you run them in order of operational value. Start with the broadest attack path, then drill into the specific opportunities it reveals. Each result shapes what you do next.

Query 1: Shortest Paths to Domain Admins - always run this first. It shows every route from any node in the domain to a DA account, ranked by number of hops.

# In BloodHound CE: Analysis tab > Shortest Paths > Shortest Paths to Domain Admins
# What to look for:
- Any path with 3 hops or fewer is immediately exploitable
- HasSession edges are the highest priority - credentials in memory NOW
- ACL edges (WriteDACL, GenericWrite) mean no exploitation needed

In the Syntex domain you should see a path similar to this:

JSMITH@SYNTEX.LOCAL --[MemberOf]--> IT-HELPDESK@SYNTEX.LOCAL --[AdminTo]--> SYNTEX-WS01.SYNTEX.LOCAL --[HasSession]--> ADMINISTRATOR@SYNTEX.LOCAL --[MemberOf]--> DOMAIN ADMINS@SYNTEX.LOCAL

Read this chain out loud: jsmith is in IT-Helpdesk. IT-Helpdesk has local admin on SYNTEX-WS01. An Administrator has an active session on SYNTEX-WS01. That Administrator is a Domain Admin. Three pivots from jsmith to full domain compromise.

Query 2: Find All Domain Admin Sessions - shows every machine where a DA account is currently logged in. These are your priority lateral movement targets.

# Analysis > Domain Information > Find All Domain Admin Sessions
Expected result: ADMINISTRATOR has an active session on SYNTEX-WS01
This confirms the HasSession edge in Query 1 is live

Query 3: List all Kerberoastable Accounts - every account with a registered SPN. These are your offline cracking targets.

# Analysis > Kerberos Interaction > List all Kerberoastable Accounts
Expected results in Syntex domain:
  svc-backup@syntex.local    (SPN: backup/SYNTEX-DC01)
  svc-sql@syntex.local       (SPN: MSSQLSvc/SYNTEX-DC01:1433)
  svc-iis@syntex.local       (SPN: HTTP/SYNTEX-DC01)
  svc-monitor@syntex.local   (SPN: monitor/SYNTEX-DC01)

# Click each account to see its privileges
# svc-sql is the highest value - SQL service accounts often have DA or local admin

Query 4: Find AS-REP Roastable Users - accounts with Kerberos pre-authentication disabled. No credentials needed to request their hash.

# Analysis > Kerberos Interaction > Find AS-REP Roastable Users (DontReqPreAuth)
Expected results:
  mwebb@syntex.local
  dfox@syntex.local
  svc-backup@syntex.local    (also Kerberoastable - double opportunity)

Query 5: Find Principals with DCSync Rights - any account that can dump all AD hashes without touching LSASS. This is instant game-over.

# Analysis > Active Directory Rights > Find Principals with DCSync Rights
# Look for accounts outside of Domain Admins / Domain Controllers
# Any regular user or service account with DCSync rights is a critical finding
★
CREST CPSA Exam Point: You must know these five queries by name and understand what each one reveals. The exam will present you with a BloodHound-style scenario and ask you to identify the attack path or explain why a specific edge is dangerous. HasSession is consistently the most operationally valuable edge - it shows where to go right now, not just what might be possible.

Documenting the Attack Path

Reporting
Why documentation is part of the attack

BloodHound gives you the map. Your job is to translate that map into a clear narrative that explains - to a non-technical reader - exactly why the attack is possible and what the business impact is. A finding that says "BloodHound found a path" is worthless. A finding that says "a standard helpdesk user can reach Domain Admin in three steps because of these specific misconfigurations" is a HIGH finding that gets fixed.

For each path identified, document it in this format. This is the structure a CPSA report uses:

## Finding: Attack Path to Domain Admin via Session Hijacking
## Severity: CRITICAL

Attack Chain:
  1. jsmith (IT-Helpdesk member) has local admin on SYNTEX-WS01
     via IT-Helpdesk group membership (AdminTo edge)

  2. The domain Administrator account has an active session on SYNTEX-WS01
     (HasSession edge - credentials are in LSASS memory)

  3. With local admin on SYNTEX-WS01, attacker can dump LSASS
     using Mimikatz to extract the Administrator NT hash

  4. NT hash used for Pass-the-Hash to authenticate as Administrator
     to the Domain Controller

  5. Full domain compromise achieved

Steps to reproduce:
  evil-winrm -i SYNTEX-WS01 -u jsmith -p Password1
  [upload mimikatz]
  sekurlsa::logonpasswords
  [extract Administrator NTLM hash]
  impacket-psexec -hashes :<NTHASH> administrator@SYNTEX-DC01
⚠
Scope Note: In this lab, document the path fully but only execute as far as your lab scope allows. In a real CPSA engagement, document everything BloodHound reveals - even paths you do not exploit - because the client needs to see the full attack surface, not just what you clicked on.

Knowledge Check

Q1. A BloodHound query shows: jsmith --[MemberOf]--> IT-Helpdesk --[AdminTo]--> WS01 --[HasSession]--> Administrator. What does the HasSession edge tell you operationally?

A. Administrator has logged into WS01 at some point in the past
B. Administrator has an active logon session on WS01 - their credentials are in LSASS memory right now
C. Administrator can log into WS01 using their credentials
D. WS01 has administrator-level access to the domain

Q2. Why does bloodhound-python run from Kali rather than running SharpHound on the target Windows machine?

bloodhound-python collects the same AD data over LDAP and SMB using valid credentials, but runs entirely on the attacker's Linux machine. No binary is transferred to the target, leaving no artefacts and avoiding AV detection. SharpHound is more reliable for active session collection but is frequently flagged by AV and leaves traces on the target system.

Q3. BloodHound shows that svc-sql has a Kerberoastable edge AND is a member of the Server Operators group. Why is this account the highest priority Kerberoasting target?

A. Because it has the most SPNs registered
B. Because Server Operators can log on locally to Domain Controllers - cracking this account's password gives DC access
C. Because service accounts always have weak passwords
D. Because it is also AS-REP roastable

Q4. What is the first BloodHound query you should always run on a new engagement, and why?

"Shortest Paths to Domain Admins" - because it immediately shows every route from any node in the domain to a DA account, ranked by number of hops. It gives you the full attack surface in one query and tells you exactly which paths are shortest (and therefore fastest to exploit). Every other query drills into specific opportunities this one reveals.

Key Takeaways

  • BloodHound models AD as a graph - it finds attack paths no manual enumeration can reliably discover
  • bloodhound-python collects from Kali with zero footprint on the target - preferred for stealth
  • HasSession edges are the highest operational priority - they show where privileged credentials are in memory right now
  • Always run "Shortest Paths to Domain Admins" first - it maps your entire route before you move
  • Every edge is an action - understand what each one lets you do, not just what it represents
  • Document attack paths in full even if you don't exploit them - the client needs to see the complete attack surface
