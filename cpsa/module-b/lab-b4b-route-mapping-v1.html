Background - How Traceroute Works

Traceroute exploits the IP Time-to-Live (TTL) field. Every router that forwards a packet decrements the TTL by 1. When TTL reaches 0, the router discards the packet and sends an ICMP Time Exceeded message back to the sender. By starting with TTL=1 and incrementing, you map each hop along the path.

Kali ----[TTL=1]----> Router 1 drops it, replies ICMP TTL Exceeded Kali ----[TTL=2]----> Router 1 forwards ---> Router 2 drops it, replies Kali ----[TTL=3]----> Router 1 ---> Router 2 ---> SYNTEX-LNX01 replies normally Result: 3-hop path. Kali - Router1 - Router2 - Target

A hop showing * * * means that router received the packet but chose not to send an ICMP reply. This is common on firewalls and network appliances. It does NOT mean the path beyond is blocked.

🎯
CREST Exam Focus: You need to understand what asterisks mean in traceroute output, what TTL is, and why a filtered hop doesn't prevent the destination from being reached. These come up in the written paper.
Part 1 - Basic Traceroute
1
Run traceroute to SYNTEX-LNX01

By default, traceroute on Linux uses UDP probes. Replace TARGET_IP with your SYNTEX-LNX01 address.

# Default UDP traceroute
traceroute TARGET_IP

Each line shows one hop: hop number, IP address, and three RTT measurements.

Record your traceroute output
2
Switch to ICMP traceroute

Some environments block UDP probes but pass ICMP. The -I flag switches to ICMP Echo Requests, similar to what ping uses.

# ICMP-based traceroute - requires root
traceroute -I TARGET_IP
Did the results differ from Step 1? How?
3
TCP traceroute on port 22

Firewalls often let TCP traffic through when they block ICMP/UDP. Tracing on a specific TCP port can reveal a route that other methods miss. Port 22 (SSH) is open on SYNTEX-LNX01.

# TCP SYN traceroute to port 22
traceroute -T -p 22 TARGET_IP
Any difference in hops visible vs. ICMP traceroute?
ℹ
In a lab environment all three methods will likely show the same path. In a real engagement with multiple firewalls you may see different hops appear or disappear depending on the probe type.
Part 2 - MTR (Matt's Traceroute)
4
Run mtr for continuous path monitoring

MTR combines ping and traceroute. It runs continuously, showing loss percentage and jitter at each hop - more useful for spotting intermittent filtering than a single traceroute run.

# -n skips DNS lookups (faster), -c sets packet count
mtr -n -c 10 --report TARGET_IP

The --report flag makes mtr run for 10 packets then exit. Without it, mtr runs interactively (press q to quit).

Record the mtr output - note the Loss% column for each hop

Part 3 - nmap Traceroute Integration
6
Use nmap's built-in traceroute

Nmap can trace routes during a scan. This combines path mapping with port discovery in a single operation - useful for correlating filtering positions with port states.

# Scan top ports AND trace route simultaneously
nmap -sS --traceroute -F TARGET_IP

Look for the TRACEROUTE section in the output after the port table.

Port states explained: Open = port is reachable and listening. Closed = port is reachable but nothing listening. Filtered = something between you and the host is blocking the probe - nmap never gets a reply. A filtered hop in traceroute and filtered ports in nmap at the same position is strong evidence of a firewall.

Part 5 - Exam-Style Questions
🎯
Answer from memory first. These questions are typical of the CPSA written paper.
Q1

What IP field does traceroute manipulate to discover each hop along the route?

Q2

A hop in your traceroute shows * * *. You then run a port scan and the target responds. What does the asterisk output tell you about that hop?

Q3

What is the default probe protocol used by traceroute on Linux? Name an alternative you could use if that protocol is blocked.

Q4

An nmap scan returns a port as filtered rather than closed. What does this tell you about the network path?

Q5

You run traceroute to a target and get 12 hops. You run it again 5 minutes later and get 14 hops. What could explain the different hop count?

Answer Key
✓
Q1: TTL (Time to Live)
Q2: The device at that hop received the probe but chose not to send an ICMP Time Exceeded reply - common on firewalls/ACLs. It does not mean the path is blocked beyond that point.
Q3: Default = UDP. Alternatives = ICMP (-I flag) or TCP (-T flag)
Q4: A packet filtering device (firewall, ACL) between the scanner and the host is dropping probes to that port without sending a response.
Q5: Asymmetric routing or load balancing - different packets took different paths through the network. The internet uses multiple redundant paths.
