Port Scanning - Techniques and Interpretation

Perform TCP and UDP port scans against live targets, compare scan types, understand the difference between filtered and closed ports, and document findings in a format suitable for a penetration test report.

Scenario

Host discovery is complete. You have identified two live hosts in the Syntex Solutions environment: a Linux server (SYNTEX-LNX01) and a Windows domain controller (SYNTEX-DC01). Your next task is to enumerate the open ports on both targets. You need to understand exactly what is listening, what scan types reveal different results, and how to avoid common mistakes that cause CREST examiners to mark candidates down.

Learning Objectives
  • Perform a full TCP SYN scan and interpret open, closed, and filtered states
  • Understand why UDP scanning is unreliable and how to work around it
  • Use version detection to enrich port scan output
  • Compare results from a default scan vs a full port scan
  • Correctly interpret nmap output as expected in a CREST exam
  • Produce a clean port matrix for two targets ready for a pentest report

Part 1 - TCP Scanning SYNTEX-LNX01
1
Default SYN Scan

Start with nmap's default SYN scan. This scans the top 1000 most common ports. It is fast and stealthy compared to a connect scan - it never completes the TCP handshake.

# Default SYN scan - top 1000 ports
sudo nmap -sS -v <LNX01-IP>

Look at the output carefully. Note the STATE column: open, closed, or filtered.

ℹ
Port states: open = something is listening. closed = port reachable, nothing listening (RST returned). filtered = no response, likely a firewall dropping packets. This distinction matters in the exam.
Record the open ports from the default scan
2
Full Port Scan

The default scan only covers 1000 ports. Services running on non-standard ports will be missed. A full port scan covers all 65535 TCP ports.

# Full TCP port scan - all 65535 ports
sudo nmap -sS -p- <LNX01-IP>

# Same scan with timing - T4 is aggressive, suitable for lab environments
sudo nmap -sS -p- -T4 <LNX01-IP>
⚠
Exam technique: In a real engagement and in the CREST exam, always run a full port scan. Candidates who only scan the top 1000 ports miss services and lose marks. Show your examiner that you know the difference.
Did the full scan find any ports the default scan missed? List them.
3
Version Detection

Open ports tell you what is listening. Version detection tells you what software and version is running. This is critical for vulnerability identification.

# Version detection on open ports
sudo nmap -sS -sV -p 21,22,139,445,2049 <LNX01-IP>

# More aggressive version detection (0-9 scale, 5 is default)
sudo nmap -sS -sV --version-intensity 9 -p 21,22,139,445,2049 <LNX01-IP>

Check the VERSION column in the output. You should now see software names and version numbers rather than just service guesses.

4
UDP Scanning

TCP scanning is reliable - the three-way handshake gives you a clear open/closed signal. UDP is connectionless: if no response comes back, the port could be open (service received but did not reply) or filtered. This makes UDP scanning slow and less certain.

# UDP scan - top 20 most common UDP ports only (faster)
sudo nmap -sU --top-ports 20 <LNX01-IP>

# UDP with version detection to reduce false positives
sudo nmap -sU -sV --top-ports 20 <LNX01-IP>
★
CREST Exam Point: You must be able to explain the difference between open|filtered and open for UDP ports. open|filtered means nmap received no response - the port may be open or a firewall may be dropping packets silently. You cannot be certain without a version probe that gets a reply.
List any open or open|filtered UDP ports found
Part 2 - TCP Scanning SYNTEX-DC01 (Windows DC)
5
Full SYN Scan Against the Domain Controller

A Windows domain controller exposes a very different port profile to a Linux server. AD DS, Kerberos, DNS, LDAP, RPC, WinRM, and IIS may all be running. Your job is to map every listening service.

# Full port SYN scan with version detection
sudo nmap -sS -sV -p- <DC01-IP>

# Save output to a file for your notes
sudo nmap -sS -sV -p- -oN syntex-dc01-portscan.txt <DC01-IP>
✔
Output formats: -oN saves normal (human-readable) output. -oX saves XML (useful for tools like Metasploit). -oG saves grepable format. -oA saves all three at once. Good habit: always save your scan output.

7
Targeted Scans on Interesting Ports

Once you have your full port list, run targeted scans on the services that matter most for Active Directory enumeration.

# Focused scan on AD-critical ports with maximum version detail
sudo nmap -sS -sV -p 88,389,445,3389,5985 <DC01-IP>

# Check if SMB signing is disabled (critical finding)
sudo nmap --script smb2-security-mode <DC01-IP>

# Check SMB version (SMBv1 is a critical vulnerability)
sudo nmap --script smb-protocols <DC01-IP>
★
CREST Exam Point: SMB signing disabled and SMBv1 enabled are both reportable findings. If the smb2-security-mode script returns "Message signing enabled but not required" - that is a finding. An attacker can perform NTLM relay attacks against machines with signing disabled.

Part 3 - Scan Comparison and Reporting
8
Connect Scan vs SYN Scan

You have been using SYN scans (-sS). A connect scan (-sT) completes the full TCP handshake. Run both and compare what gets logged on the target.

# TCP connect scan (does NOT require root)
nmap -sT -p 22,445 <LNX01-IP>

# SYN scan (requires root, does not complete handshake)
sudo nmap -sS -p 22,445 <LNX01-IP>
ℹ
Why this matters: A connect scan (-sT) completes the three-way handshake and will appear in application logs. A SYN scan (-sS) sends only the initial SYN and drops the connection on SYN-ACK - it is less likely to appear in application logs, but will still be seen by IDS and firewall logs. Neither is truly invisible.
In your own words: what is the practical difference between -sS and -sT for a penetration tester?
