Part 0 - Understanding DNS and dig
Before you touch any tools, read this. DNS is the phone book of the internet. Every device on a network has a name, and DNS maps that name to an IP address. When you are on an engagement, DNS is one of the first things you query - not because you are attacking DNS itself, but because a DNS server holds a map of everything on the network. If you can get that map, you know what targets exist before you have scanned a single port.

Why dig instead of nslookup? nslookup is the Windows tool most people know. It works, but it hides information and behaves inconsistently across platforms. dig (Domain Information Groper) is what pentesters and sysadmins use because it shows you the raw DNS response - exactly what the server sent back. On a CREST exam and on real engagements, dig is the tool you use.
Why This Matters to a Pentester
DNS reveals the attack surface. Every hostname in DNS is a potential target. Mail servers, internal admin panels, staging environments, old forgotten servers - they all show up in DNS if the zone is configured sloppily.
DNS misconfigurations are common and critical. A zone transfer that is open to the world is a critical finding. It hands you the complete internal hostname list in one command - something that would take hours of active scanning to discover any other way.
DNS is passive from a network perspective. Querying DNS does not set off IDS alerts the way a port scan does. You are sending normal DNS queries - exactly what every computer on the network does all day. This makes it one of the least detectable forms of reconnaissance.

DNS record types - what they reveal

DNS stores different types of records. Each type tells you something different about the target. This is what you are looking for when you query DNS on an engagement:

Record TypeWhat It StoresWhy a Pentester Cares
A Hostname to IPv4 address The basic building block - gives you IPs for every named host. Find vpn.target.com and you have found the VPN gateway.
AAAA Hostname to IPv6 address Often forgotten in security controls. IPv6 addresses may bypass firewalls that only filter IPv4.
MX Mail server hostnames and priority Identifies mail infrastructure. Mail servers are often less hardened than web servers and are prime phishing or relay targets.
NS Authoritative name servers for the domain Tells you which servers hold the zone. These are your targets for a zone transfer attempt.
TXT Arbitrary text - SPF, DKIM, DMARC, verification tokens Weak SPF (~all) means you can spoof email from the domain. Missing DMARC means phishing emails will land in inboxes. Sometimes contains internal notes or credentials left by mistake.
CNAME Alias pointing to another hostname Can reveal cloud infrastructure (s3.amazonaws.com), internal staging environments, or takeover-vulnerable subdomain aliases.
SOA Start of Authority - zone metadata Contains the primary nameserver, admin email address (useful for OSINT), and zone serial number.
AXFR Zone Transfer - a copy of the entire zone The jackpot. If allowed, returns every single record in the zone. This is a critical misconfiguration.

Anatomy of a dig command

dig follows a consistent pattern. Understanding it means you can build any query you need:

# Full syntax
dig [@server] <name> [type]

# Example: ask the DNS server at 10.1.1.10 for the A record of syntex.local
dig @10.1.1.10 syntex.local A

# If you leave out @server, dig uses your system's configured DNS resolver
# On an engagement you almost always specify @server to query the target directly

# The +short flag strips the metadata and shows just the answer
dig @10.1.1.10 syntex.local A +short

# axfr is a query type, not a flag - same syntax as any other record type
dig axfr @10.1.1.10 syntex.local
✓
The @server part tells dig which DNS server to ask. Without it, your query goes to your own machine's configured resolver - which knows nothing about the target's internal domain. Always specify @<TARGET_IP> when querying an internal domain.
Part 1 - DNS Enumeration (Internal)
This section queries the internal Syntex lab DNS server. Use the <TARGET_IP> your instructor gave you. The domain is syntex.local - this is the internal Active Directory domain for the Syntex organisation. You are querying it directly because you are inside the network.
ℹ
DNS runs on port 53. On a Windows domain controller, the DNS service is almost always running because Active Directory depends on it. The DC is both the AD controller and the DNS server for the internal domain.
1
Query DNS record types against the internal Syntex domain

Use dig to query the target's DNS server directly. This tells you what records are exposed and what services are running internally.

# Query A record - what IP does this hostname resolve to?
dig @<TARGET_IP> syntex.local A

# Query all record types at once
dig @<TARGET_IP> syntex.local ANY

# Query MX records - what mail servers does this domain use?
dig @<TARGET_IP> syntex.local MX

# Query NS records - what name servers are authoritative for this zone?
dig @<TARGET_IP> syntex.local NS

# Query TXT records - SPF, DMARC, or anything stored as text
dig @<TARGET_IP> syntex.local TXT
Record your DNS findings
2
Attempt a DNS zone transfer against the internal domain

A zone transfer copies the entire DNS zone to another server. This is a legitimate mechanism - secondary DNS servers use it to stay in sync with the primary. The problem is when a DNS server is configured to allow zone transfers from anyone, not just authorised secondary servers.

Try it against the internal Syntex domain. This requires you to be inside the lab network:

# Attempt AXFR zone transfer against the internal domain
dig axfr @<TARGET_IP> syntex.local

The result will be one of two things. If the transfer succeeds, you will see every DNS record in the zone - hostnames, IPs, mail servers, internal services - all in one response. If it fails, you will see Transfer failed: REFUSED or Transfer failed: SERVFAIL.

Your instructor has set up a real BIND9 DNS server on the internet with allow-transfer { any; }; configured. This is exactly the misconfiguration you would find on a real engagement. The server is:

This server is hosted on Azure and is intentionally misconfigured for training purposes. Do not attempt to interact with it in any other way - zone transfer queries only.

Why This Matters to a Pentester
This is a real finding. On a genuine engagement, finding an open AXFR on a public DNS server is a critical vulnerability. You are about to do exactly what an attacker does on day one of a real penetration test.
Zone transfers reveal the full network map. Internal hostnames, service accounts referenced in TXT records, mail infrastructure, internal IP addresses exposed through A records - all of it comes back in one query. This is information that would take hours to enumerate any other way.
The impact is reconnaissance, not direct compromise. AXFR itself does not give you access to anything. What it gives you is a complete target list. That is stage one of every attack chain.
3
Enumerate DNS records for syntexsolutions.net

Before attempting the zone transfer, run the standard record queries against the public domain. This builds your picture of the target's external infrastructure.

# Query the NS records first - confirm which nameserver is authoritative
dig syntexsolutions.net NS

# Query A record via the authoritative nameserver directly
dig @20.24.202.6 syntexsolutions.net A

# Query MX records - what mail servers does the company use?
dig @20.24.202.6 syntexsolutions.net MX

# TXT records - SPF, DMARC, any other configuration
dig @20.24.202.6 syntexsolutions.net TXT
ℹ
Look at the SPF record carefully. A ~all (tilde) in the SPF record means soft fail - email from unknown sources will still be delivered. A well-configured domain uses -all (hard fail). Weak SPF is a phishing enabler and is worth flagging in a report.

Part 2 - SMB Enumeration
SMB (Server Message Block) is the Windows file-sharing protocol. It runs on port 445. In this lab you are querying the internal Syntex lab VM using the target IP your instructor gave you. Use <TARGET_IP> for all commands in this section.
Why This Matters to a Pentester
SMB null sessions are still found in the wild. A null session is an anonymous connection to SMB with no credentials at all. Modern Windows defaults block this, but legacy systems, NAS devices, and misconfigured servers still expose it. On internal networks you will find it regularly.
Share enumeration reveals data stores. Even if you cannot read the files, knowing a share called IT_Backups or Finance_Reports exists tells you exactly where to focus once you have credentials.
IPC$ null sessions enable user enumeration. The IPC$ (inter-process communication) share is used for named pipes. On some configurations, connecting to IPC$ anonymously lets you enumerate local users and groups - that is your starting point for password spraying.
⚠
SMB (port 445) is one of the most dangerous services to expose. Null sessions - anonymous connections with no credentials - allow share enumeration on misconfigured Windows hosts.
5
List SMB shares with a null session

A null session uses an empty username and password. The -N flag tells smbclient not to prompt for a password. The -L flag lists available shares.

# List shares on the target - null session (no credentials)
smbclient -L //<TARGET_IP> -N

# If the target is a Windows domain member, also specify the domain
smbclient -L //<TARGET_IP> -N -W SYNTEX

# If you are getting authentication errors, try specifying empty credentials explicitly
smbclient -L //<TARGET_IP> -U "" -N

Shares ending in $ are hidden administrative shares. C$ is the full C drive, ADMIN$ is the Windows directory, IPC$ is the inter-process communication share. These exist on every Windows machine. Any share without a $ is a custom share that someone created.

SMB enumeration results
6
Connect to a share and list contents

If you found any readable shares, try connecting. The -N flag skips the password prompt.

# Connect to a specific share anonymously
smbclient //<TARGET_IP>/<SHARENAME> -N

# Once connected, useful smbclient commands:
# ls                 - list files and directories
# get filename       - download a file to your local machine
# mget *             - download all files
# exit               - disconnect
✓
On a real engagement, finding a world-readable share is always worth documenting even if it looks empty. Configuration files, old backups, scripts with hardcoded credentials, and forgotten documents with passwords in the filename have all been found on "empty" SMB shares. Download everything and search it offline.

Part 3 - LDAP Anonymous Bind
LDAP (Lightweight Directory Access Protocol) is the query interface for Active Directory. It runs on port 389. Use <TARGET_IP> for all commands in this section. The domain is syntex.local.
Why This Matters to a Pentester
LDAP is the front door to Active Directory. Everything stored in AD is accessible via LDAP - user accounts, groups, computer accounts, password policies, service accounts. If you can query it without credentials, you get the full user list immediately.
Even a failed bind is useful. If LDAP is running and the port is open, Active Directory is running. That shapes your whole attack plan - you know Kerberoasting is on the table, you know you are hunting domain credentials, you know password spraying is worth attempting.
Anonymous bind is not the only path. Even when anonymous bind is blocked, any valid domain account can query LDAP. Getting any single set of domain credentials opens the full directory to you.
ℹ
LDAP (port 389) is the query interface for Active Directory. An anonymous bind - connecting without credentials - is allowed by default on some older AD configurations. Even a failed anonymous bind confirms LDAP is running, which means Active Directory is present.
7
Attempt an LDAP anonymous bind and enumerate the directory

ldapsearch queries LDAP directories. The -x flag means simple authentication (not SASL). An empty bind DN with no password attempts an anonymous bind - connecting without credentials.

# First attempt - try querying the base DN anonymously
ldapsearch -x -H ldap://<TARGET_IP> -b "" -s base

# If the base DN query works, try enumerating user accounts
ldapsearch -x -H ldap://<TARGET_IP> -b "DC=syntex,DC=local" "(objectClass=user)" sAMAccountName

# Enumerate groups - what groups exist in the domain?
ldapsearch -x -H ldap://<TARGET_IP> -b "DC=syntex,DC=local" "(objectClass=group)" cn

# Enumerate computer accounts - what machines are domain-joined?
ldapsearch -x -H ldap://<TARGET_IP> -b "DC=syntex,DC=local" "(objectClass=computer)" cn

If anonymous bind is blocked, you will see ldap_bind: Inappropriate authentication (48). This still tells you LDAP is running. If it succeeds, you will get directory objects back.

Part 4 - SNMP Enumeration
SNMP (Simple Network Management Protocol) runs on UDP port 161. It is used to manage and monitor network devices - routers, switches, servers. Use <TARGET_IP> for all commands in this section.
Why This Matters to a Pentester
SNMP exposes the device configuration. A successful SNMP walk against a router or switch returns interface IP addresses, routing tables, ARP cache, running processes, software versions, and hardware serial numbers. This is essentially a full device inventory handed to you without authentication.
Default community strings are everywhere. public is the default read community string in SNMPv1 and v2c. Devices ship with it enabled and network teams often never change it. Finding a device with SNMP and the default community string is a common finding on internal tests.
SNMP runs on UDP - easy to miss. Most port scans default to TCP. UDP scanning is slower and noisier. SNMP at port 161/UDP is often overlooked, which is exactly why querying it manually before nmap is worthwhile - you might find it before an automated scan would.
⚠
SNMP runs on UDP port 161. SNMPv1 and v2c use community strings as the only authentication. The default read community string is public. If this is not changed, an attacker can read the full device configuration - interface IPs, running processes, software versions - without any credentials.
8
Query SNMP with the default community string

snmpwalk walks the SNMP MIB (Management Information Base) tree and returns everything the device exposes under a given OID. We start with the default community string public and SNMPv2c.

# Walk the full SNMP tree with the default community string
snmpwalk -v2c -c public <TARGET_IP>

# Query specific OIDs - system description (OS, version, uptime)
snmpwalk -v2c -c public <TARGET_IP> 1.3.6.1.2.1.1.1.0

# Running processes - what software is active on the host?
snmpwalk -v2c -c public <TARGET_IP> 1.3.6.1.2.1.25.4.2.1.2

# Network interfaces and their IPs
snmpwalk -v2c -c public <TARGET_IP> 1.3.6.1.2.1.2.2.1.2

# Try the other default community strings if public fails
snmpwalk -v2c -c private <TARGET_IP>
snmpwalk -v2c -c manager <TARGET_IP>

If the community string is correct you will see a large amount of output. If SNMP is not running or the string is wrong, you will see Timeout: No Response from <TARGET_IP>.

SNMP enumeration results
✓
If public does not work, try private (the default write community string), manager, and the target organisation's name or abbreviation. Community strings are often set to company names. syntex, SYNTEX, or the company's city name are worth trying.

Q2

You run dig axfr @20.24.202.6 syntexsolutions.net and receive the full zone. Write out three distinct types of information a pentester can extract from this zone transfer output and explain why each is useful.

1. Internal hostnames and IPs - reveals the network map including servers that are not externally accessible (BMGDC01, BMGFS01, etc). Every hostname is a potential target. 2. Q3

What is a null session in the context of SMB, and why is it a security concern?

A null session is an anonymous connection to an SMB server using an empty username and password. It is a security concern because on misconfigured systems it allows an unauthenticated attacker to enumerate shares, user accounts (via IPC$), and sometimes read sensitive file content - all without any credentials. Modern Windows defaults block null sessions, but legacy systems and misconfigured servers still allow them. Even share enumeration without file access tells an attacker exactly where sensitive data is stored.
Q4

SNMP is running on a target. The community string public returns data. What security version of SNMP is this, and what is the primary weakness?

SNMPv1 or v2c - both use community strings as cleartext authentication passed in every packet. The community string travels in plaintext and can be captured by anyone on the network path. SNMPv3 addresses this with proper authentication (MD5/SHA) and optional encryption (DES/AES). Using the default public community string is a critical misconfiguration - it means the device has essentially no authentication. The read community string gives full read access to device configuration; the write community string (often private) allows configuration changes.
Q5

What port does LDAP run on, and what does a successful anonymous bind tell you about the target environment?

LDAP runs on port 389 (636 for LDAPS over TLS). A successful anonymous bind means the server allows unauthenticated queries to the directory. On Active Directory this can expose the full user list, group memberships, computer accounts, and password policy without any credentials. The presence of LDAP itself strongly suggests Active Directory is in use - this tells you Kerberos is available, that Kerberoasting may be viable, and that domain credential harvesting is the primary attack path.
Q6

Explain the difference between dig syntexsolutions.net NS and dig @20.24.202.6 syntexsolutions.net NS. When would you use each?

Without @server, dig sends the query to your machine's configured DNS resolver (usually your ISP or corporate DNS). With @20.24.202.6, dig queries that specific server directly. For external domains, querying without @server works because public DNS resolvers know the answer. For internal domains (syntex.local), you must use @server to query the target's DNS server directly - your resolver has no idea what syntex.local is. For testing specific server behaviour (like AXFR), you always use @server to target the nameserver you want to test, regardless of whether the domain is internal or external.
